# Buddy eval v0

B02's small, offline-first parse harness (TD-067). The owner chose OpenAI `gpt-6-luna`; this is not a provider bake-off. Three short synthetic messages cover English, Arabic and Arabizi. `cases/smoke.yaml` holds exact parse expectations; aliases are explicit, numbers/units/state exact, ambiguity candidates separate from client question policy.

- `make eval`: builds the private .NET CLI, replays hand-authored synthetic `fixtures/*.json` through the real OpenAI SDK/`IChatClient`/`ILlmClient`, runs Dart graders, writes `reports/B02-offline.{md,json}`. No credentials or network calls to OpenAI. CI runs this mode only.
- `make eval-live`: **paid**, explicit. At most three fixed prompts, sequential, no retries/repair/fallback; first provider failure stops. Reads only `~/.config/fitness-buddy/openai-api-key` (0600), inside the CLI. Never supply the key in command arguments or commit it. The CLI rejects unknown/duplicate IDs and changed message text. Writes `reports/B02-live.{md,json}` even for a partial/failed smoke; no prompts, provider error bodies or raw model content in reports.
- `make eval-schema`: regenerate the committed internal JSON schema from C# records; review and commit it alongside prompt/schema changes. This is not an app contract: B08 owns the generated public API contract.

The CLI uses a local JSONL pipe with no HTTP listener or database. Regular API startup exposes no Buddy route and never loads this key. Live usage has a 1200-output-token cap per request, low effort, a 20-second deadline; cancellation/timeout is not proof a provider didn't charge. Estimated USD uses standard short-context rates dated 2026-10-16 ($0.10 input/$0.01 cached/$0.50 output per million), excludes taxes/other billing adjustments and is not the invoice. `store:false` disables stored Responses state, not standard abuse-monitoring retention.

Offline reports prove plumbing only. Three live samples cannot establish AQ-02/03/06/07/11 quality, AQ-12 p90, production latency or language equivalence. B08/B15 and A21 keep the broader acceptance work. No model judge or nightly paid run is installed. Future live runs need the owner's explicit testing scope; don't treat `make eval-live` as a routine verification command.

## B08 public endpoint eval

`cases/m3.yaml` adds 26 synthetic fixtures covering T01–T16, T19, T39–T41 and Arabic/Arabizi variants (10/26). These are hand-authored parser responses with separate public expectations. The backend's `BuddyPublicEvalTests` starts a real authenticated loopback HTTP server, passes the fixtures through the official SDK, validates/resolves them, then runs `bin/public_eval.dart`. It covers actual UTF-8 request bytes, discriminated intents, food facts, amounts/units, states and dimensions. T41 covers the resumed request and replay seam; the app offline queue remains A23.

`make test-dotnet` includes this offline gate. The report is `backend/artifacts/buddy/B08-offline.json`; CI uploads it and the separate `eval` job validates required cases, all parse/resolution checks, and the Arabic/Arabizi quarter. The gate reuses the dotnet run rather than rebuilding. Full question-policy and nutrition AQ metrics remain A21/B09/B15; fixture scores are not paid-model quality measurements.

The public CLI reads a private JSON configuration from stdin (`endpoint`, temporary `token`, `deviceId`, `now`, `mode`, `report`, optional allowlisted `caseIds`). Tokens never appear in argv or reports. HTTPS is required except loopback tests; redirects are refused. Use a fresh synthetic account/run because message IDs are stable within the fixture run. Reports contain case IDs, booleans, status and timings only. `lib/public_eval.dart` supplies deterministic graders independently of the transport.

The owner authorized **up to 10 physical OpenAI sends for B08 on 2026-10-21**, including repairs. Only the explicitly gated `BuddyLiveTests` path may use that scope. It checks the real API and published catalog on the laptop, with a durable private counter at `~/.local/state/fitness-buddy/B08-openai-20261021.count`; the fence commits before transport dispatch and cannot be reset as routine testing. Normal tests return without entering that path. Live results go to `reports/B08-live.json`, without content or credentials. The small sample measures connectivity/regressions/latency only, not broad AQ acceptance.

## B09 interpretation eval

`cases/b09.yaml` holds 53 synthetic cases for the interpret-v2 intents (B09a WP5). They cover T03, T20–T29 and DY-045, plus edges: the AI-091 newest-slot ask and unqualified newest, `referenceNotFound`, scope all, an empty-target day/slot lookup, a relative edit → `clarify unsupported` (PA15), a transcribed `date:` hint, a numeric date read day first, saved meals both ways, "save this" with and without a card, memory remember/portion/forget, batches (open, portion, rest, close, no open batch), personal foods (components, stated figures) and active-card follow-ups ("make it 2 eggs", "another egg", "no toast", "bulgur not rice", AR/Arabizi). 17/53 cases are Arabic or Arabizi.

Each case has a recorded v2 `parsed` output, its own request `context` (case-local IDs) and `activeProposal`, and `expected.intents`: partial public intents. The grader (`gradeIntents`) checks the kind sequence, language and script. Each top-level expected field becomes its own check (`targets`, `candidates`, `patch`, `batchId`, ...): maps match by their expected keys, lists by length and position, scalars exactly. Every case, M3 included, also gets the PA5 `provenance` check: every UUID in the response must be an ID from the request context (recentEntries, savedMeals, openBatches, personalFoods or activeProposal). Slot and request IDs never come back.

`BuddyPublicEvalTests.B09_intent_fixtures_pass_real_HTTP_SDK_resolver_and_Dart_grader` runs it the same way as M3 (config `caseFile: b09`) and writes `backend/artifacts/buddy/B09-offline.json` next to `B08-offline.json`. Reports break results down by `byLanguage` (`en`/`ar`/`arabizi`: Arabizi script, Arabic letters, else English) next to `byScript`. CI's `eval` job runs `tools/scripts/check-buddy-eval.py` on both reports from the repo root. For b09 it requires every case in the file, T03/T20–T29/DY-045, the per-case check set derived from `expected`, the Arabic/Arabizi quarter and the three breakdown keys.

This is interpretation-level grading only (D13). Engine-level AQ metrics through the real ProposalEngine are B09b (T03, T24, M3) and the A25–A27 exit criteria (edits, memory, batches; PA11). Fixtures prove the pipeline, not model quality.
