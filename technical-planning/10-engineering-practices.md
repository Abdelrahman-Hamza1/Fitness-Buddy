_How we keep a solo-built, two-language codebase healthy enough to reach R3._

## 2. Code conventions

**Both stacks**
- Immutability by default. Explicit result types for expected failures. Exhaustive `switch` over sealed types.
- No `now()` or `random` in domain or application code: inject Dart `Clock` / .NET `TimeProvider` and ID generators.
- **Comments: the right amount, not the most** (TD-054). A comment earns its place by saying what the code can't: *why* this way, a non-obvious constraint, a trap, the spec/TD/plan ID behind a rule (`/// Implements AI-060, AI-061.`). Don't restate the code, narrate the history ("moved from…", "review r1 fix"), or repeat the same rationale in several files: say it once where it matters and reference it.
  - Public APIs (barrels, ports, `*.Contracts`): a short doc comment on what it is and its contract (one to three lines is typical).
  - Private code: none when names and types already say it; a line where a reader would otherwise stop and wonder.
  - Long rationale belongs in the plan, a TD or a README, not in a block comment.
- A one-line justification (maintenance, licence, size) for every new dependency, in the PR.

**Dart / Flutter**
- `dart format`, `very_good_analysis`, zero warnings. freezed models, sealed unions.
- No logic in widgets: widgets render state and forward intents, view models orchestrate, rules live in `fb_domain`.

**C# / .NET**
- `dotnet format`, .NET analyzers (`AnalysisMode=latest-recommended`), **warnings as errors**, nullable reference types on.
- Records for DTOs and value objects. `sealed` by default. `internal` by default inside modules.
- Minimal API endpoints are thin: bind → call handler → map result. No business logic in endpoints or EF entities' setters.
- Async all the way, with a `CancellationToken` on every I/O call.

## 3. Enforced architecture rules (CI)

| Rule | Check |
|---|---|
| `fb_domain`, `fb_text`, `fb_api_client` have no Flutter or I/O dependencies | Pure Dart packages + a dependency allowlist test |
| App features import each other only via barrels (and the other layer boundaries of `03` §3.2) | `tools/app_check` (`make app-check`, in `check-dart`) |
| Only `ChangeSetApplier` writes user tables | Library-private write APIs + an architecture test |
| No `left/right` layout, no raw strings in widgets | `tools/app_check` (rules `directional`, `raw-string`) |
| Backend layer direction (Domain ← Application ← Api/Infrastructure) | **ArchUnitNET** tests |
| Backend modules don't reference each other's internals or tables | ArchUnitNET + `internal` visibility + one schema per module |
| The API matches the contract | Conformance diff (S02) |
| No breaking change to a published API version | `oasdiff` |
| API style | Spectral |
| No user content in logs | Unit tests on log scrubbers (both stacks) |

## 4. Testing strategy

The pyramid is weighted toward pure logic, where the product promises live:

| Level | Scope | Tools | Target |
|---|---|---|---|
| **Domain (Dart)** | Nutrition math, yields, ProposalEngine, targets/rebalancing/floors, trend, adaptive TDEE, PRs, notification planner, Ramadan calendar, QueryEngine, user model, validators | `test` + **property tests** (`glados`): rebalanced days never below the floor (SF-010), weekly sum preserved (TG-041), trend within input range, recompute idempotent | ≥ 95% line coverage on `fb_domain` |
| **Text (both)** | Normalization, Arabizi aliases, number/unit parsing | Shared golden YAML (`contracts/testdata/`) | Every bug → a case |
| **App data** | DAOs, repositories, migrations, FTS search, outbox triggers | drift in-memory DB, drift migration tests | Every schema version |
| **Backend domain & application** | Handlers, rules, mappers | xUnit v3, fakes for ports | All handlers |
| **Backend integration** | Repositories, migrations, RLS, sync rules, jobs, outbox | **Testcontainers** (real Postgres 18) + `WebApplicationFactory` | All modules |
| **Adapter contract tests** | Every `ILlmClient`, `IEmailSender`, `IOpenFoodFactsClient` adapter | Shared test suite per port, recorded fixtures | Every adapter |
| **API contract** | Conformance, breaking changes, style | Conformance diff, oasdiff, Spectral | Every PR |
| **Sync** | Convergence simulation, fault injection, version skew, OF-03 | Dart simulator + real API in Docker | Must pass (`05` §5.3) |
| **Widget / golden** | Design-system components + key screens: light/dark, text scale 1.0/2.0, LTR (+ RTL for components) | `flutter_test`, `alchemist` | Design system 100% |
| **Integration / E2E** | Journeys J1, J4, J5, J7, J8, J12 (offline), guest sign-up, export | **patrol** on an emulator + the local API | Before each release |
| **AI acceptance** | AQ-01–12 | `tools/buddy_eval` | Thresholds in `spec/40` §2 |
| **Performance** | Cold start, Today screen, Buddy round trip | Integration test with timeline on the A55 | Budgets in `09` §6 |

**Test data:** synthetic only. Real messages enter the repo only when the owner exports them (TQ-07).

## 5. Requirement traceability (AT-001)

- Tests name the requirement they prove: `test('AI-060 asks only above threshold', …)` in Dart, `[Trait("Req", "AC-012")]` in C#, or a `// covers: AI-060` comment.
- Rules without a spec ID use `[Trait("Rule", "<doc>.<section>-<slug>")]` plus a one-line class comment (e.g. `09.4-logging`); never tag them as a `Req`. Dart tests name the rule without a spec-ID prefix.
- `tools/trace` (built in S01) parses `spec/*.md` for R1 IDs and scans both test trees. It reports implemented / tested / missing per release.
- Each step card lists its spec IDs. The traceability report is the "is R1 done?" dashboard.

## 6. Git & workflow

- **Trunk-based on `main`** (renamed from `master` in S01). Short-lived branches per step: `step/A06-diary-domain`, with Conventional Commits. `main` gets **one squash commit `Sxx: <name>` per step**, whose body keeps the branch's commit subjects (TD-036). **Every change to `main`** (steps, docs, Dependabot, hotfixes) **goes through a CI-verified SHA**: the ruleset requires the `ci` check, blocks force pushes and deletions, and there are no PRs (TD-039, `13` §3.E).
- **Conventional Commits** (`feat(diary): …`, `fix(api): …`). Release notes come from the `main` commit bodies + step Outcomes.
- **Step checklist** (run-step E, squash commit body): step ID + spec IDs · tests added · migrations + migration tests if the schema changed · contract updated + client regenerated if the API changed · eval run if AI-related · screenshots if UI · runbook updated if ops changed · no new warnings.
- Unfinished work merges behind feature flags.
- **Releases:** API: tag `api-vX.Y.Z` → prod deploy. App: tag `app-vX.Y.Z` → store tracks. Contract: `contracts-vX.Y.Z` marks a published contract (the oasdiff baseline); the first, `contracts-v1.0.0`, is created with the first `app-v*` release that calls the API (TD-044).

## 8. Environments

See `08` §2. The app's `dev` flavor points at the local API (`make up`), `staging` at the staging API, `prod` at production. Until production (B14) the staging and prod builds point at the laptop test server (B03, TD-064).

## 9. Definition of Done (every step)

1. Implements its step card's spec IDs. Any deviation is first recorded as a spec decision (`spec/decisions.md`) or a TD (`12`).
2. Domain and handler logic unit-tested, including the edge cases named in the spec text.
3. UI: empty, loading (skeleton) and error states (UX-050–052), light/dark, text scale 2.0, golden tests.
4. Works offline where the spec says it must (`spec/20` §3).
5. Writes go through change sets: undo for direct actions, proposals for AI.
6. Strings in ARB. No `left/right`.
7. API changes: contract first, client regenerated, conformance green, no unintended breaking change.
8. Traceability tags in tests. CI fully green. Eval green if AI-related.
9. Performance budget checked if the step touches a hot path.
10. Docs updated: the step card's **Outcome** section, any changed planning doc, runbooks, new TDs.

## 10. Documentation

- `technical-planning/` holds the architecture, decisions and steps. An outdated doc is a bug.
- Every package and module has a short README: purpose, public API, how to test.
- `docs/runbooks/` from B14 (`08` §8).
- The root `README.md` explains setup in under 10 minutes: prerequisites, `make setup`, `make up`, `make test`, running the app against the local API.
