### 1. Validation: built-in `AddValidation()` wins
| Option | Pros | Cons | Maintenance / licence |
|---|---|---|---|
| **Built-in** `AddValidation()` (`Microsoft.Extensions.Validation`, in the shared framework, no package) | Zero dependency. Runs for query, header and body parameters, nested records/lists. Output is `HttpValidationProblemDetails` through `IProblemDetailsService`, so `CustomizeProblemDetails` applies. Attributes feed the OpenAPI schema | `errors` keys are C# member names (`Qty`, `Items[0].Qty`), not JSON names. Rules are attributes (async/cross-service rules do not fit). Only `Resolvers` and `MaxDepth` options | Ships with ASP.NET Core 10 (MIT), patched with the framework |
| FluentValidation 12.2.0 (2026-10-10, Apache-2.0) | Expressive, testable rules | Docs: no automatic validation for Minimal APIs ("isn't supported out of the box"), needs manual calls or a 3rd-party filter package (SharpGrip, ForEvolve). No OpenAPI constraints unless another lib is added. Extra package and vendor | Active, single maintainer, no licence change found |

Verified behaviour (10.0.12):
- Invalid body → 400 `application/problem+json` `{"type","title","status","errors":{"Name":[...],"Items[0].Qty":[...],"Child.Code":[...]},"traceId","requestId"}`. With `CustomizeProblemDetails` the `type` can be set to `/errors/validation-failed` for `HttpValidationProblemDetails`.
- **Gotcha 1:** keys are PascalCase member names. camelCase them in `CustomizeProblemDetails` (rebuild the `Errors` dictionary, lower-case the first char of each path segment) so they match JSON names.
- **Gotcha 2:** malformed JSON (`{"title":`) is NOT a validation failure: plain 400 with `type` = the RFC 9110 link, no `errors`. Map it in `CustomizeProblemDetails` (owner/orchestrator choice: reuse `/errors/validation-failed` or add a catalogue entry).
- **Gotcha 3 (records):** `public record Req([Required] string Name, [Range(1,10)] int Qty)` validates at runtime but the OpenAPI schema gets NO `minimum/maximum`. Use `[property: Range(1,10)]` (validates AND documents). Using both forms reports each error twice. For query parameters `[Range]` appears as `minimum/maximum` directly. `required` comes from record parameters regardless.
- **Gotcha 4:** the generated OpenAPI document lists only `200` for these endpoints: 400/429/426 must be declared (`.ProducesValidationProblem()` / `.ProducesProblem()` or the operation transformer). Not tested whether `ProducesValidationProblem()` emits the contract's `ProblemDetails` schema; check against `contracts/openapi` in the plan.
- Validation can be turned off per endpoint with `.DisableValidation()`. A third-party blog reports that validation is skipped for endpoints/DTOs defined in external class libraries (unverified). The Host-assembly design (module endpoints are mapped from the Host, DTOs may live in module assemblies) must be tested with a DTO in a second project: source generator runs per project that references the attributes.

### 4. Rate limiting
- Built in: `AddRateLimiter` + `RequireRateLimiting(policy)` / `UseRateLimiter()` (after `UseRouting`, i.e. implicit in minimal APIs; after `UseForwardedHeaders`). Fixed/sliding window, token bucket, concurrency, `RateLimitPartition` by key. Rejected requests: `RejectionStatusCode` (default 503, set 429); `OnRejected` receives `Lease`, `MetadataName.RetryAfter` is available only for limiters that supply it (fixed window did). **Nothing writes `Retry-After`, `RateLimit` or `RateLimit-Policy` for you** (scratch app: 200 responses had no rate-limit headers; I set `Retry-After` in `OnRejected`, and the body had to be written there too).
- IETF draft `draft-ietf-httpapi-ratelimit-headers-11` (2026-05-23, expires 2026-11-24, still a draft): `RateLimit-Policy: "default";q=100;w=60` (quota, window seconds) and `RateLimit: "default";r=50;t=30` (remaining, seconds to reset). Policy names are quoted structured-field strings; earlier drafts used different syntax (`limit/remaining/reset`), so the format may still move. Source: [datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/), [-11 text](https://www.ietf.org/archive/id/draft-ietf-httpapi-ratelimit-headers-11.txt).
- The built-in limiters don't expose per-partition "remaining" on a successful request (only `RateLimiter.GetStatistics()` on a concrete limiter, which a partitioned limiter hides). So emitting `RateLimit` on 2xx needs a small custom limiter wrapper or own counters. **Plan for S03:** emit on 429 only: `Retry-After` (seconds), `RateLimit-Policy` (static from the policy options), `RateLimit: "<policy>";r=0;t=<retryAfterSeconds>`, plus the problem body `/errors/rate-limited`. Emitting on every response is a later enhancement (own `IRateLimiterPolicy` returning a custom limiter), and the contract should document only what is promised. Runtime test needed for the 429 problem (status without framework default, S02 note).
- Partition key by IP: `ctx.Connection.RemoteIpAddress` after `UseForwardedHeaders`. Behind kamal-proxy (verified in kamal-proxy `internal/server/target.go`): with `forward_headers: false` (the default when `ssl: true`) the proxy **overwrites** `X-Forwarded-For`/`-Proto`/`-Host` with the real client values (`req.SetXForwarded()`); with `true` it appends to what the client sent. Docs: [Kamal proxy](https://kamal-deploy.org/docs/configuration/proxy/). So with a single proxy hop the XFF is trustworthy.
- ASP.NET Core trust: default `ForwardedHeadersOptions` trusts **loopback only**, so out of the box nothing is forwarded from a Docker bridge peer. Don't use `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` (docs warn it clears KnownProxies/networks: trusts everyone). Use: `ForwardedHeaders = XForwardedFor | XForwardedProto`, `ForwardLimit = 1`, and add the Docker network of kamal-proxy to `KnownIPNetworks` from config (e.g. `172.16.0.0/12`, make it an option `Proxy:TrustedNetworks`). **`KnownNetworks` is obsolete in .NET 10 (ASPDEPR005 warning; our build treats warnings as errors): use `KnownIPNetworks`.** Stage 2 (Hetzner LB in front of kamal-proxy): `forward_headers: true` and `ForwardLimit = 2`. Whether the app container is reachable from other hosts directly (published port) must be checked in S05/S29: Kamal app containers are not normally published, unverified here. Source: [Proxy/load balancer docs, 10.0](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0).
- Behind the proxy `RemoteIpAddress` stays the proxy IP if the trust list is wrong: add a test (`X-Forwarded-For` honoured from a trusted peer, ignored from an untrusted one) and a startup log line of the trusted networks (not IPs of clients).
**Recommendation:** built-in limiter with IP partition, custom `OnRejected` writing problem+json, `Retry-After`, `RateLimit-Policy`, `RateLimit` (429 only in S03).

### 5. Request correlation
- Verified in ASP.NET Core 10.0.12: `HttpContext.TraceIdentifier` is Kestrel's connection-based id (`0HNP…:00000001`), unrelated to the trace; it is writable. The framework's problem-details `traceId` extension is **`Activity.Current.Id`, the full W3C string** (`00-<traceid>-<spanid>-<flags>`), not the bare trace id. Inbound `traceparent` is honoured by the server activity (same TraceId, ParentSpanId kept) even without OTel installed (framework Activity); ILogger scopes carry `TraceId`/`SpanId`.
- Options: (a) `traceparent` only: clients must send it (the app does not), so the server would be the origin and the client has nothing to quote except a body field; (b) separate `X-Request-Id`: extra id to join with traces; (c) **one id**: `X-Request-Id` = `Activity.Current.TraceId` (32 hex). If the caller sends a valid `X-Request-Id` (≤64 chars `[A-Za-z0-9._-]`), echo it as the response header and add it as a log scope / activity tag `fb.request_id`, but still generate the trace from `traceparent`/new trace. Set `HttpContext.TraceIdentifier` to the chosen value so framework logs use it.
- Problem body: keep the extension small. Override `traceId` in `CustomizeProblemDetails` with the bare 32-hex id (same as the header) and do not add a second `requestId` field (the scratch app's `requestId` = connection id, useless to a client). The contract declares `XRequestId` response header (components/headers.yaml) but no response references it; the plan must attach it to every response in the OpenAPI document (a transformer; oasdiff can't compare response-header schemas, oasdiff #1094, per S02 note) and add `traceId` as an optional string to `ProblemDetails` in the contract before emitting it (extensions are allowed by the description).
- Echo must also happen on errors thrown before routing (rate limiter 429, 426 gate, exception handler): register the request-id middleware first (after forwarded headers), and set the header in `OnStarting` so it survives `UseExceptionHandler` re-execution (header set in the scratch app's early middleware appeared on the 400; the exception path wasn't checked for the header: test it).
**Recommendation:** (c), with W3C `traceparent` accepted and propagated by default, no new request header from the app.

## 2026-10-16 — B01 sync escape hatch and sequence safety

PowerSync remains a credible alternative, rather than a service adopted in this
step. The official [Flutter SDK guide](https://docs.powersync.com/client-sdks/reference/flutter)
describes a backend connector that supplies credentials and uploads local

disconnected. We would still own upload validation and conflict/history policy.
The official [Drift integration guide](https://docs.powersync.com/client-sdks/orms/flutter-orm-support)
uses `drift_sqlite_async` and currently labels ORM support beta, including a
local-only table notification caveat. Adopting it would change A01/A34's database
integration, so the existing SyncEngine boundary remains useful.

PowerSync's [self-hosting guide](https://docs.powersync.com/intro/self-hosting)
supports Docker deployments. Its [self-hosted instance configuration](https://docs.powersync.com/configuration/powersync-service/self-hosted-instances)
requires source replication, bucket storage (Postgres or MongoDB), client auth
and sync-stream configuration. Postgres can remain the only database engine,
but the extra sync service and storage/configuration still add operations.
**Inference for Fitness Buddy:** keep the custom path if the spike's real-server
convergence/history/fault results hold; PowerSync reduces download machinery,
but does not remove our business conflict/recovery/auth responsibilities.
No PowerSync dependency, deployment or paid account was added.

Postgres [sequence functions](https://www.postgresql.org/docs/18/functions-sequence.html)
allocate independently of transaction rollback; even `ON CONFLICT` may consume
values. **Design inference:** sequence values alone are not a commit-order
cursor. B01 serializes each user's pushes before allocation, permits gaps and
returns only the last delivered sequence. A real Postgres test blocks a second
push behind an uncommitted first allocation, then checks both pages after
commit. Never replace this with an unconstrained sequence maximum.

Initial laptop result: 1,000 fake scenarios and 50 Docker API scenarios pass;
5,000 small synthetic rows pushed in 3,096 ms and fresh-pulled in 174 ms over
Docker loopback (not a Wi-Fi measurement). Formal post-review evidence belongs
