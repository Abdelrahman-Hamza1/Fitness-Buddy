# B06 — Account deletion (backend)

| Track | Depends on | Size | Owner | Status |

_Old ID: S28 server part (renumbered by TD-063, 2026-10-16). The app side is A35._

**Goal.** A real account deletion that removes everything the server holds for a user, idempotently, with tokens revoked at once.

**Spec:** AC-031, AC-040, PR-11, C-4 (server side) · **Decisions:** TD-022, TD-025

## Scope
- **Contract first:** `DELETE /v1/me` (+ a status read if completion is asynchronous). Commit it and note it in the Progress log so A35 can build against it.
- **Account module:** create a deletion request → **integration events** (outbox) to each module (Identity: identities and tokens; shared signing/wrapping keys remain; UserData: documents + history; Usage: counters; Buddy: idempotency records) → each module deletes its data for the user idempotently → mark complete. Tokens revoked immediately. Audited (no content).
- A test that **no rows remain for the user in any schema** after deletion. Modules added later register their deletion handler (an architecture test fails if a module with user data has none).

## Out of scope
- The app flow (A35). Backups age out within 30 days (`08` §5); nothing is deleted from backups.

## Decide in the low-level plan
- Whether deletion completes synchronously in the request or in the worker (with the app polling).

## Exit criteria
- [ ] Integration test: after deletion, a query across all schemas finds zero rows for the user. Old refresh tokens fail.
- [ ] Deletion is idempotent (a retry after a partial failure completes).
- [ ] Contract conformance green; the Dart client regenerated.

### Design and decisions

- **D1 · Synchronous atomic deletion.** Choose a single database transaction for this modular monolith: serialize on B05's per-user lock, revalidate the trusted active session through Identity's public contract, record the deletion intent, revoke sessions/mark deleting, deliver database-only module deletion handlers and remove the account before commit. Return `204` only after durable commit. If any participant fails, **all** DB effects including revocation roll back; no partial deletion is reported successful, and the same authenticated request can retry. No polling endpoint, receipt token, second secret or persistent completed user record. Idempotency means repeated effects are harmless; after a successful commit old credentials return401 (including a retry after a lost response), never regain access to replay a204. Document that distinction for A35; do not weaken authentication to make response replay possible. If measured transaction duration makes synchronous completion unsuitable, revisit the plan before introducing an asynchronous partial-state lifecycle.
- **D2 · Module boundaries and outbox.** Account orchestrates a public deletion participant contract and a content-free typed integration event (user ID and event ID only). Each module owns its erasure SQL. Extend the existing outbox dispatcher so the request can dispatch this **database-only** event inside the supplied transaction, with the same processed-message dedup semantics as worker delivery. Do not implement a second event mechanism, open nested transactions or call network/file adapters from handlers. The completed deletion envelope/processed markers are removed before commit, in the same transaction as all effects; rollback preserves both data and the retryable original request. A worker must never observe a half-deleted user or replay a completed erasure. Explicitly test lost connection before/after commit and the request/worker claim race. Ordinary events retain S04 delivery/retry semantics.
- **D3 · Exact erasure inventory.** Identity removes provider identifiers/email, devices, sessions, refresh-token hashes, user-linked audit rows and link challenges, then the user. Resolve email-associated sign-in challenges/address throttles using Identity's own normalized-address HMAC before dropping the identity, without deleting another account's state; global IP throttle buckets stay as abuse controls without user linkage. Identity's ES256 signing keyring, AES wrapping keys and email pepper are installation-wide and must **not** be deleted for one account. UserData removes documents (including compacted fences), history and version receipts; global dataset metadata/sequences stay. Buddy/Usage currently have no user tables: register explicit empty participants and require real erasers as they acquire user storage. Catalog is global-only and declares that fact. Account deletes its own intent/progress/audit mapping at completion. No retained row may identify the erased user, even if it contains no content.
- **D4 · Infrastructure caches and queue records.** Inventory `ops.idempotency`, jobs, user-scoped schedules, outbox, processed markers, pending/dead items and any response bytes; deletion must remove every user-linked record and must not be undone by a worker already holding a claim. `ops.idempotency` currently stores only a hashed scope, so first add nullable indexed `user_id` ownership for authenticated replay records and populate it in the generic writer; migrate/expire pre-existing legacy replay rows safely (at most24h, with a proven ownership strategy or pre-release cache invalidation), without touching other users' responses. Put erasure in an Ops-owned public primitive, never Account SQL against `ops` tables. Use one explicit order: global recovery lock when needed → per-user advisory lock → idempotency/queue row lock → module rows. QueueProcessor first discovers a candidate without locking, acquires that candidate's user advisory transaction lock (if user-scoped), then claims that exact row with `FOR UPDATE SKIP LOCKED` and revalidates state/type/user/due time; if changed/unavailable it releases the transaction and selects again. It never holds a queue row while waiting for a user lock. Global jobs that enumerate users enqueue user-scoped work instead of acquiring a user lock after a queue claim. Workers re-check lifecycle before effects; orphaned or deleting-user work is consumed/erased without recreating user rows. Generic IdempotencyMiddleware acquires the user lock and live-session check **before** its key lock/cache read, including replay hits, and before writing a response. Test existing replay bytes racing deletion, not just new endpoint execution. Purge markers by joining the user's message IDs before deleting envelopes. The deletion endpoint is not enrolled in generic response caching, and its own completion must not insert a replay record or queue marker after the purge.
- **D5 · RLS and capabilities.** Reuse user-scoped `DatabaseSession` and module-owned deletion methods wherever existing grants permit them. Identity exposes only narrow authenticated-session begin/delete capabilities with fixed trusted search paths, explicit grants, forced RLS and no arbitrary table/user SQL. The coordinator receives IDs only from the validated principal; never request body/query IDs. New functions stay inside the already accepted audited deletion/Identity exception in `04` §6, with exact function inventory/grant tests; no general cross-schema security-definer function. A deleting user cannot refresh/sign in/link concurrently and recreate old-owned rows. All mutations that can outlive auth validation participate in the lifecycle locking fence (B05 sync plus Identity auth functions and user queue handlers). No signing-key rotation/deletion here.
- **D6 · Coverage enforcement and bounded residuals.** Add a module user-data classification/participant inventory checked by architecture tests: every installed module declares user-owned tables and eraser, or explicitly global-only. Integration tests additionally inspect actual DB ownership columns/FKs and known hashed ownership paths; do not rely solely on a hand-written list that could omit a new table. Future Buddy/Usage user stores must fail that test until registered. Completed erasure produces only aggregate/content-free telemetry, with no durable user mapping; audit the action while pending and erase that mapping at completion. Existing backups age out within30days, as planned; do not rewrite snapshots or delete shared recovery secrets. Laptop email files contain short-lived codes, not durable account storage: remove matching outstanding deliveries through a separate idempotent local cleanup phase where feasible, and distinguish credential expiry from physical erasure: codes expire at10min, running-process reaping occurs on the next ≤1min sweep, but a stopped laptop/process cannot physically delete files on a wall-clock deadline. Startup prunes expired deliveries **before readiness/traffic**, and unsafe/unwritable cleanup leaves the adapter unready; test stopped/restarted/failing cleanup. These files cannot be counted as immediate DB erasure; after account deletion no surviving code can authenticate the old identity/session. Recovery safety is D7 below, delivered now for the laptop rather than deferred to B14.
- **D7 · Deletion-safe recovery barrier (laptop first).** No per-user deletion ledger is retained. Protect a global opaque recovery generation outside the restorable DB/dump, in the existing private operator state directory, plus its matching global DB metadata row and backup manifest field. This is backup control metadata, not another service/vendor; contains no user identifiers. All deletion, backup, restore and reset operations coordinate under one database/global recovery lock plus the private controller lock where applicable; deployment is single-host until B14 supplies an equivalent durable mechanism. Before beginning any erasure effects, reserve a fresh generation and durably write it outside the DB (atomic replace, file+parent fsync), then record it in the same DB transaction as deletion. Only then may deletion commit/respond204. Backup obtains the same recovery lock **before** exporting a consistent snapshot, records the matching generation and dump digest in its private manifest, and publishes the manifest atomically. Restore checks the protected external generation and manifest before changing the live DB: a legacy/missing/mismatched generation is rejected, including all snapshots before the latest deletion. Restoring a matching snapshot additionally rotates B05's dataset epoch before opening traffic. The Host verifies DB/external generation equality both for readiness **and before serving online Identity/user-data requests**; a503 health result alone is insufficient because Tailscale can reach the API directly. Thus a manual stale restore or interrupted deletion cannot quietly reopen old accounts. A crash between external fence and DB commit may over-block recovery/readiness; it must never permit resurrection. Missing/corrupt/lost external fence is fail-closed: verified recovery or a deliberately clean server reset is required, not inference from a stale backup. Known transactional rollback may be reconciled only while holding the same locks with verified current DB state; no automatic generation rollback after an ambiguous commit. Introduce a fresh post-deletion safe backup in the operator flow; retain older backup files until their planned expiry but mark them unusable for a direct live restore. Do not auto-delete or overwrite the owner's backups. Document the availability limitation (old snapshots need an explicit offline sanitization procedure or clean reset) and test it on isolated synthetic stacks. B14 adapts this existing guard to production; neither a dataset UUID nor an old dump is sufficient evidence of deletion safety.

### Risks and handoff

The key risk is a request authenticated before deletion committing data afterward; the common user lock plus in-transaction live-state check is mandatory, not just middleware auth. Other risks are hidden replay bytes/hash-only ownership, shared signing keys mistaken for per-user keys, and a success/processed marker reintroducing a user row after purge. Measure large synthetic accounts; never return204 before commit to hide timeouts. No paid service or AI calls. A35 receives generated DELETE plus explicit idempotency/local-wipe semantics; no Flutter edit is authorized here. If atomic synchronous deletion cannot meet measured resource limits, or restore/residual handling would require accepting a new security trade-off, prepare a concrete revised plan for the owner before implementation of that change.
