_New step (owner phone feedback, 2026-10-30). Phase 1, wave 1 (TD-105). Tier: Normal._

**Goal.** Fix what the owner felt on the phone in the first prod build: chip rows that jump, an abrupt range switch, a weight card that takes too much room, tabs that keep stale screens, and a dark default the owner no longer wants.

**Spec:** UX-040 (light default, D-083), HM-005 (slim weight row, D-084), UX-010 (tabs) · **Decisions:** D-083, D-084, TD-107, TD-104 (lean tests)

## Scope
- **Steady chips:** fixed-width chips on the weight graph range row and every other chip/button row (the weigh-in sheet included), so a selected chip never resizes its row. Audit every chip row in the app.
- **Range switch:** a short transition when the weight graph range changes, instead of an instant jump.
- **Light by default** (D-083, TD-107): the stored theme default, the pre-read first frame and the Android window/splash become light; System/Light/Dark stay.
- **Slim weight row on Today** (D-084): with a weigh-in today, one row "weight · trend · ＋" (row opens the graph, ＋ logs a weigh-in); the full card only when there is no weigh-in today.
- **Tabs:** switching away from a tab resets it to its root screen; tapping the current tab again scrolls it to the top.

## Out of scope
- New screens or features. Workout row on Today (A37a).

## Exit criteria
- [ ] No chip row in the app changes width when a chip is selected (checked on every chip row; one widget test for the shared chip).
- [ ] A fresh install opens in light, first frame and splash included; a stored Dark still applies.
- [ ] Today shows the slim row after a weigh-in and the full card before (widget test).
- [ ] Tab reset and re-tap scroll-to-top work (widget test).
- [ ] Owner phone check on the A55 (collected, non-blocking).

## Low-level plan
_Written 2026-10-30 by the step planner (Opus) against `main` fe4f671, with A46 (`origin/step/A46-test-diet`) and A16's plan (`origin/step/A16-progress-tab`) read for overlap. Tier: **Normal** (no write path, no sync, no AI; the theme default is a read default)._

### 1. Summary
After A45, **selecting a chip never changes its size** anywhere in the app: `FbChoiceChip` (the chip every selection row already uses) drops the leading check for a size-neutral selected style, `FbUnitPicker` is rebuilt on it, and Material chips lose the checkmark. The weight graph's range row keeps a reserved slot for "Today", and the **chart eases between ranges** (300 ms, none under reduced motion). The app **opens in Light** (unset setting, first frame, Android window and splash); a stored Dark or System still applies. **Today shows a slim weight row** (weight · trend · ＋) on a day with a weigh-in and the full card otherwise. **Tabs reset to their root when you leave them**, and re-tapping the current tab scrolls it to the top (or pops to root). A screen with unsaved edits is never thrown away by a tab tap: a switch keeps it, and a re-tap asks first and goes to the root only after a confirmed discard.

### 2. Decisions
| # | Decision | Why |
|---|---|---|
| D1 | **Steady selected style, no checkmark.** A selected chip = the brand tint (`primaryContainer`, text `onPrimaryContainer`) **plus a 2 dp `primary` border** (unselected: `surfaceContainer` + 1 dp `outline`). The text weight doesn't change, a leading `icon` stays in both states (today the check *replaces* it), and the border is painted by the `Material` shape, not laid out, so **nothing in the layout depends on `selected`**. Fill and border ease over `FbMotion.fast` (zero under reduced motion). Chips get a `minWidth` of 48 dp (with the existing 48 dp `minHeight`), content centred: short labels ("1M", "kg") become even targets and pass the tap-target size. **TD candidate** (small): a DS convention note on TD-076, "selection = tint + 2 dp border, never a size change", replacing A02's "tint + check" | The check (18 dp + 8 dp gap) is what pushes the width (owner item 1). A reserved check slot would make every unselected chip ~26 dp wider: 5 range chips would no longer fit one line at the A55's 379 dp content width. The border weight is the non-colour cue, so UX-071 holds; T3 proves its contrast |
| D2 | **`FbChoiceChip` *is* the one steady chip: no new component.** Every selection row in the app already uses it (audit, §3.2), so the fix lands in one file and every row follows. `FbUnitPicker` (weigh-in, food sheet, entry amount, Buddy line row) switches its internals from Material `ChoiceChip` to `FbChoiceChip(dropdown: false)`, so all unit rows look the same (the weigh-in sheet and weight history used two different chips). `FbAnswerChip` (Buddy) stays a Material `ChoiceChip`; the chip theme sets `showCheckmark: false` and a constant-width border (2 dp transparent / 2 dp `primary` when selected), and `FbAnswerChip` drops its `showCheckmark: selected` | One place to keep steady. **A16 merge order doesn't matter:** A16 plans `FbChoiceChip` as its fallback, and that chip becomes steady whichever step merges first |
| D3 | **Value chips stay as they are.** Chips showing a label + a picked value ("When · Today, 08:05", "Meal · Lunch") change width only when a picker returns a new value. That's a content change after a choice, not a jump on tap; the audit table records them | Out of the card's "selected chip" scope; fixing them would mean fixed widths for free text |
| D4 | **Range row: the "Today" chip's slot is always reserved.** `GraphRangeChips` keeps the Today chip laid out (`Visibility(maintainSize/State/Animation)`), hidden, excluded from semantics and not tappable until the window is panned. Panning no longer adds a chip that wraps the row and pushes the graph down | Same glitch, other trigger. Shared by the weight and measurement graphs |
| D5 | **Range switch: the chart eases its window.** `FbTimeSeriesChart` tweens from **the window on screen** (the old `range` shifted by the pan offset) to the new `range` over `FbMotion.slow` with `FbMotion.curve`, through `FbMotion.of(context, …)` (reduced motion → jump). A pan's drag end hands back exactly the window on screen, so from == to and nothing moves. **Interruption (PA1): a drag that starts mid-tween commits the target first**: `onHorizontalDragStart` stops the controller and sets the shown window to `widget.range`, then the pan runs from there, so the painted window, the drag clamping and `_dragEnd` all use the same base and panning is never blocked (at most the rest of a 300 ms zoom is skipped). The painter reads the animated window through a listenable (repaint only, no rebuild), as it already does for the pan offset. Fallback if it stutters on the A55: an `AnimatedSwitcher` crossfade of the chart keyed by range (same file) | A zoom between ranges keeps the user oriented; a fade is the cheap fallback. A16's other charts can reuse it |
| D6 | **Light default = the setting's default.** `AppSettings.theme.defaultValue` → `ThemePreference.light`. An unset key reads as the default and a stored value keeps its meaning, so users who never chose land on Light and a stored Dark, Light or System still applies. **Unset and chosen are *not* always distinguishable (PA3):** `SettingsActions._set` skips the write when the picked value equals what it reads, so a pick equal to the default of its time was never stored. Two historical cases now read Light: **System picked while System was the default** (A10 until A44) and **Dark picked while Dark was the default** (A44, 2026-10-29/30). No code (R1 has one user, and the store can't tell these from never-chosen); the owner summary and the Outcome say: "if you'd picked a theme before, check it once in Me › Settings › Theme" | TD-107 / D-083 as approved; no migration possible or needed |
| D7 | **First frame and Android window become light, day and night.** `app.dart` already maps "not read yet" to `defaultValue` (comments only). Android: `fb_window_background` = the light surface `#FFFAF9F4`. `LaunchTheme`/`NormalTheme` parents become `@android:style/Theme.Light.NoTitleBar` (also in `values-v31`), with `android:statusBarColor` = the window colour and `android:windowLightStatusBar` = true (API 23+, minSdk 26), so the launch status bar isn't black on cream. Still no `values-night`. **Pre-12 splash:** the reversed mark (cream + mint) would vanish on cream, so `launch_background.xml` gains a 160 dp oval in `@color/ic_launcher_background` (the flavor plate) under the mark. Android 12+ already draws the plate (`windowSplashScreenIconBackgroundColor`). Trade-off, mirroring A44 D7: Dark users, and System users on a dark phone, see one light → dark switch after frame 1 (no animation, A10 D6) | The default is the common case; day/night resources would flash for every default user with a dark phone |
| D8 | **Kept golden `app_shell.png`:** its "dark" cell gets a stored Dark (override `themePreferenceProvider`) instead of only a dark system, so the key-screen golden still shows the dark theme | With a Light default, the "dark system" cell would silently turn light |
| D9 | **Slim row condition:** a **readable weigh-in on the page's own day** (`WeightCardState.weighedInOnDay`, computed in `weightCardProvider` from `latest.localDate == date`). It applies to every day page (HM-009, "the same layout shows past days"): a past day with a weigh-in is slim, a past day without one keeps the full card that invites one for that day | D-084 speaks of "today"; past pages follow the same rule so the pager reads the same |
| D10 | **Slim row content:** one tappable row inside the `FbCard`: "{that day's latest weigh-in} · Trend {trend}" (one line, wraps at large text) → `push(TodayWeightGraphRoute)`. At the end an `FbIconButton` ＋ (tooltip/semantics from ARB, `key: WeightCard.slimAddKey`) → `showWeighInSheet(context, date: isToday ? null : date)`. The slim row has no rate, cadence note, tip or edit row. **Editing today's weigh-in moves** from one tap on Today to graph → point → edit (D-084 accepts this). The tip is neither shown nor marked shown, so it can still appear on a day without a weigh-in. Card ↔ row changes size through `AnimatedSize` (`FbMotion.of`) | D-084 as approved; two buttons give the row and ＋ distinct targets and keep UX-005 (＋, Save = 2 taps) |
| D11 | **Tab tap rules** (a pure function `tabTapAction(...)` in `lib/app/router/tab_tap.dart`). **Another tab:** go to its root (`goBranch(i, initialLocation: true)`), unless its top screen holds unsaved edits (D12); then `goBranch(i)` keeps its stack. **The current tab, deep:** if the branch holds unsaved edits, ask that screen to confirm a discard (D12) and **go to the root only after a confirmed discard** (PA2); a cancel leaves everything as it was. Otherwise go to the root. **The current tab, at root** (branch navigator `canPop()` false): fire the reselect signal (D13). A branch never visited has no navigator yet and counts as at root. **TD candidate** with D12–D13: "tab behaviour: reset on switch, re-tap = top/root, unsaved screens are kept", replacing S06 D2's "each tab keeps its stack" | Owner item 5. Material's Android bottom-navigation behaviour resets a destination to its top level. Today a re-tap already goes to the root, but it silently drops a dirty form; that bug is fixed too |
| D12 | **"Holds edits" = a registered unsaved-edits guard (PA2, replaces the `popUntil` peek).** New in `core/navigation/unsaved_edits.dart`: a widget **`UnsavedEditsGuard({required bool dirty, required Future<bool> Function() confirmDiscard, child})`** that (a) renders the `PopScope(canPop: !dirty)` itself and, on a blocked back, pops only when `confirmDiscard()` returns true; and (b) while `dirty` and mounted, registers `confirmDiscard` under its `Navigator.of(context)` in a keepAlive `unsavedEditsProvider` (`UnsavedEdits`: `bool holds(NavigatorState?)`, `Future<bool> confirm(NavigatorState)`; the latest registration wins). The router asks the registry for the branch navigator. **Another tab:** `holds` → keep the stack. **Re-tap while deep:** `await confirm(nav)`; true → `goBranch(i, initialLocation: true)`, which drops the form with the rest of the stack; false → nothing. The personal food form (the only dirty-guarded screen in a tab: Me › Your foods, Today › Add food › New food) swaps its `PopScope` for the guard, and `_confirmLeave` becomes `Future<bool> _confirmDiscard()` (shows the existing discard sheet and returns its answer; the guard does the pop). Its own save/delete exits keep setting `_leaving`, passed as `dirty: dirty && !_leaving` | The router learns the user's answer, so a confirmed discard ends at the root and a cancel stays put, with no peek idiom and no timing guesses. Any future form gets both behaviours by using the guard |
| D13 | **Re-tap scroll-to-top seam** in `core/navigation/tab_reselect.dart` (core may not import `app/`; features may not either): `enum AppTab { today, progress, workouts, me }` (order = `AppRouter.tabs`), a keepAlive Riverpod notifier `tabReselectProvider` (`fire(AppTab)` emits a new `TabReselect(tab, serial)`), and a widget **`ScrollToTopOnTabReselect`**. With no controller it animates `PrimaryScrollController.maybeOf(context)` (Progress's `ListView` and Me's `CustomScrollView` are primary by default on Android). Its `.builder` form owns a `ScrollController` for scroll views that can't be primary: Today's day pages, where all 2–3 mounted pages scroll to top, which is harmless. It scrolls to 0 over `FbMotion.slow`, or jumps when `FbMotion.of` is zero, and does nothing without clients. `appRouterProvider` passes `onReselect` into `AppRouter`, which calls the notifier. Workouts is a placeholder with nothing to scroll; A37 wraps its screen when it builds one (doc comment on `AppTab`) | Router-agnostic, testable, and inside the layer rules. The no-controller form survives A16's rewrite of `progress_screen.dart` as long as its list stays primary |
| D14 | **Tests per TD-104:** logic and risk, plus one happy-path widget test per changed screen; copy is never asserted; no new goldens. The **kept key-screen goldens that change** (chip style, theme) are regenerated **one file at a time**, after the code: `tools/scripts/heavy.sh timeout 600 flutter test --update-goldens <file>`. Expected: `weight_graph_golden_test`, `weigh_in_sheet_golden_test`, `food_sheet_golden_test`, `today_golden_test` (only if its `entry_amount_sheet` cell shows the unit picker), `personal_foods_golden_test`, `setup_golden_test`, `food_card_golden_test` (if the card shows answer chips or a unit row) and `app_shell_golden_test` (D8). CI decides the final list: any other kept golden that fails is checked for chip/theme-only diffs before it is regenerated. Today's goldens seed no weigh-ins, so D9/D10 leave them unchanged | Owner rules 2026-10-30 |
| D15 | **Start implementation after A46 is on `main`** (rebase first). A46 deletes the design-system goldens, 15 Patrol files and many copy tests that D1–D10 would otherwise churn, and it edits `weigh_in_test.dart` | Avoids regenerating ~40 DS goldens that are about to be deleted, and conflicts in the same test files |

### 3. Design

#### 3.1 Design system (`packages/fb_design_system`)
- `components/choice_chip.dart`: D1. Selection no longer swaps `icon` for `FbIcons.check`; the border is 2 dp `primary` when selected and 1 dp `outline` otherwise (`outlineVariant` when disabled); `BoxConstraints(minWidth: FbSpace.s7, minHeight: FbSpace.s7)`; the label/value column is centred when there's no value. The fill and border ease through a `TweenAnimationBuilder`/`AnimatedContainer` on `FbMotion.of(context, FbMotion.fast)`. `Semantics(selected:)` is unchanged. The doc comment states the steady contract: "**its size never depends on [selected]**".
- `components/number_pad.dart` `FbUnitPicker`: each option becomes `FbChoiceChip(label:, selected:, dropdown: false, onTap:)`, which already gives the same semantics (button, selected, label). The `Wrap` stays.
- `components/chips.dart` `FbAnswerChip`: no `showCheckmark`. `theme/component_themes.dart` `fbChipTheme`: `showCheckmark: false`; `side` = `WidgetStateBorderSide.resolveWith` (selected → 2 dp `primary`, otherwise 2 dp transparent); the doc comment is updated.
- `charts/time_series_chart.dart` (+ `time_series_painter.dart`): D5. The state gains `SingleTickerProviderStateMixin`, an `AnimationController`, and `ValueNotifier<FbChartRange> _window`. In `didUpdateWidget`, on a range change: `from = oldWindow.shift(offset)`, `_offset = 0`, animate `_window` from `from` to `widget.range` (a millisecond lerp of start and end) for `FbMotion.of(context, FbMotion.slow)`, or set it at once when that's zero. The painter takes `ValueListenable<FbChartRange> range` and repaints on `Listenable.merge([range, offset])`; drag clamping and `onRangeChanged` use `widget.range` (the target), as now; `onHorizontalDragStart` (new) commits the target if the tween is running (PA1), so all three agree before any drag delta is applied. Add `@visibleForTesting FbChartRange get shownWindow` for T4.
- `tokens/contrast.dart` / `contrast_test.dart`: a non-text pair, `primary` against `primaryContainer` and against `surface`, ≥ 3:1 in both themes (T3).
