## Scope
- **Ownership fixed 2026-10-24 (A21 PA1):** A22 creates/owns `chat_messages` and saves the message first. A23 creates/owns the drift **`proposals` table + migration (Risky)**, resolve-proposal op, status/outcome recording and consumes B18’s `chatMessage` / `proposal` sync entities. **B18 “chatMessage & proposal sync entities (server)”** is a new backend step like B17: its contract commit comes first; A23 builds against that contract (orchestrator adds board row).
- **`chat_messages` lifecycle** (`03` §6): saved as `queued` before sending → `processing` → `done` / `pending_offline` / `failed`. The **`BuddyMessageQueue`**: idempotency key = message ID, retries with backoff, processes on reconnect and app foreground (TQ-03).
- **Offline:** a message sent offline shows as "will process when you're online" (AI-047). Once processed it becomes a normal proposal.
- **Atomic per-card resolution/outcomes:** one row per meal card with immutable `originMessageId` and current `budgetMessageId`; metadata plus kind, `codecVersion`, versioned interpretation/draft JSON (interpretation holds **only this card’s normalized intents**, referring to facts/options stored once in compact card JSON), status pending/confirmed/discarded/superseded, outcome unchanged/adjusted chips/discarded and resolved_at (`05` §2.3). A21 supplies draft ops only. The confirm use case appends the version-checked resolve-proposal op to those ops in **one `ChangeSet` / `ChangeSetApplier` transaction**, with `Origin.proposal(card.id)`; include the owning assistant-message budget update in that same ChangeSet; failure rolls back diary/card-status/outcome/message-budget together. Discard resolves status/outcome without food writes. Outcomes feed `06` §5/A26 from confirmed/resolved records, never unconfirmed learning.
- **Pending proposals** (AI-045/046): kept when the sheet is dismissed. The **"N to confirm · +X kcal" strip** on Today (HM-004) reopens them. Never counted in totals or shown as diary entries (DY-025). They sync like any row (G3).
- **Failures:** AI unavailable → pending + manual search offered (AI-153). Not understood → says what it didn't get, with chips (AI-150). Vague → asks what was eaten with typical-item chips (AI-152, T11).
- **Out of scope / medical:** templated, kind declines (AI-003, SF-030, T40).
- **Language check:** a banned-word filter on all model-written text (SF-020, AI-142).
- **Chat history:** scrollback in the sheet, and **clear chat history** in settings without touching the diary (AC-033).
- **Milestone M3 run:** E2E on the M3 case set (T01–T16, T19, T39–T41) from the owner's phone, plus the eval half with `buddy_eval` (`README.md` §5).

### 1. Summary
After **A23a**, every Buddy card is a row in a new synced `proposals` table (schema **v9**), created in the same change set as the assistant reply. Card adjustments, follow-ups, confirm and discard each write the whole message session (all its cards + the assistant row's budget) in one `ChangeSet`; confirm adds the diary ops, the version-checked resolve and the outcome to that same transaction, and Undo of a confirm or discard reverts all of it. The draft codec (v2) now carries `dateHint`, `assumedAmounts` and `removedComponents`, so pending cards come back after a restart exactly as left, restored by `budgetMessageId`, with calm recovery for cards that can't be reopened or whose food facts changed. A mapper turns rows into B18 `proposal` v1 payloads and back (corpus-tested). After **A23b**, messages survive offline, errors and app kills: a frozen request snapshot is replayed with the same Idempotency-Key on reconnect/foreground with backoff; each failure says what to do; clarify/out-of-scope/medical replies use kind templates with chips; Today shows "N to confirm · +X kcal" (and messages waiting); the sheet scrolls back through history; chat history can be cleared without touching the diary. M3's app half is then demonstrable (the paid A55 run is the owner's).

### 3. Design

**3.1 Layers** (`03` §2–3, `app_check`). Domain (`fb_domain`): codec v2, `hasUserState`, `fitsSyncShape`, `proposal_ops.dart`, **`ProposalRecord`** (next to `ChatMessage`, PA8), chat op additions, `safety/moral_words.dart` + `ModelTextGuard` (A23b). Application (`features/buddy/application/`): `buddy_thread_state.dart` (`BuddyCard`, `BuddyTurn`, `BuddyThread`, `LoggedSummary`, `RemovedLine` moved mechanically out of the controller, rec R1), `ProposalSessionWriter` (pure: latest session(s) + membership → ops; the only budget-op producer), `ProposalWriteLane` (one serial lane per thread, coalesced jobs, D7/D8), `DurableProposals` (the contributor), `SessionMembership`, `ProposalOutcomes`, `BuddyThreadRestorer` (records → turns), changes to `ProposalResolution`, `SendBuddyMessage`, `BuddyThreadController` (orchestration only; target ≤ ~800 lines after the move); A23b: `BuddyMessageQueue` (the one dispatcher: timer/backoff/wakes + in-flight key set), core `apiReachabilityProvider` stream (`core/api`, D19), `BuddyFailureReplies`, `OccasionChips`, `buddyPendingSummaryProvider`, `ClearChatHistory` command. Presentation: card recovery states, pending/failed turn rows, chips, "Show earlier", strip (`features/today/presentation/pending_strip.dart`, reads only the buddy barrel), Me › Your data row. Writes only through `ChangeSetApplier`.

**3.2 Schema v9** (`core/db/tables/chat_tables.dart`, `chat.drift`, `sync_triggers.drift`, `migrations/from_8_to_9.dart`).
- `proposals` (`SyncColumns`, entity `proposal`): `kind` TEXT NOT NULL; `status` TEXT NOT NULL CHECK IN (`pending`,`confirmed`,`discarded`,`superseded`); `outcome` TEXT NULL CHECK IN (`unchanged`,`adjusted`,`discarded`); `resolved_at` INTEGER NULL; `origin_message_id` TEXT NULL; `budget_message_id` TEXT NULL; `codec_version` INTEGER NOT NULL; `interpretation_json` TEXT NULL; `draft_json` TEXT NOT NULL. No pairing CHECKs (the server checks none; the handler enforces them locally, as A22 D3). Indexes `ix_proposals_budget (budget_message_id) WHERE deleted_at IS NULL`, `ix_proposals_pending (created_at) WHERE status = 'pending' AND deleted_at IS NULL`. Triggers `proposals_outbox_ai/au/no_delete`. `SyncedTable` entry; export spec (all columns).
- `chat_messages` + `request_json` TEXT NULL, `answer_json` TEXT NULL (local-only; export includes them; the `chatMessage` mapper allowlist already excludes them).
- Migration: `createTable(proposals)`, `addColumn` ×2, both indexes, three triggers; `schemaVersion` 9; `heavy.sh make db-migrations` (dump, steps, `test/drift/user/generated/schema_v9.dart`). The test loops over every generated version.

**3.3 Ops** (handler `features/buddy/data/proposal_op_handler.dart`, registered in `app_scope.dart`).
```
CreateProposal(id, ProposalRowDraft{kind, originMessageId?, budgetMessageId?, codecVersion, interpretationJson?, draftJson})  // status pending
SaveProposalDraft(id, {expectedBudgetMessageId, budgetMessageId, interpretationJson?, draftJson})                         // content/binding only; revision ≥ stored
ResolveProposal(id, {expectedBudgetMessageId, ProposalStatus to /*confirmed|discarded*/, ProposalOutcome outcome, interpretationJson?, draftJson}) // pending only; revision ≥ stored
SetChatMessageBudget(id, codecVersion, budgetJson, {clearAnswer}) // live assistant row; revision ≥ stored; clearAnswer nulls answer_json (D14)
CreateChatMessage(id, draft, {answerJson})                     // answerJson local, assistant rows only
SetChatMessageStatus(id, v, status, {language, requestJson})   // requestJson local, user rows only; nulled at done/failed (A23b)
ClearChatHistory(cutoffMs)                                     // A23b: owns scrubbing; scrub + tombstone, plans N row writes
```
Wire checks: UUIDv7 ids/refs, `kind` ≤ 32, `codecVersion` 1…2³¹−1, JSON objects well formed; `foodLog` rows need both refs and interpretation (TD-083). Status/binding/revision rules per D6 (`proposalStale` when the incoming codec revision is lower than the stored one). Duplicate reply rule per D22 (only rows with `replyToMessageId` set). Ops have content-free `toString`.

**3.4 Persistence flows** (`ProposalSessionWriter` inside one `ProposalWriteLane` job each; ops built from the **latest** session(s) when the job runs; appended through the D8 hooks into A22's change sets).
```
reply      : [user done, CreateChatMessage(M, answerJson), SetChatMessageBudget(M), CreateProposal × cards]        (system)
adjust     : [SaveProposalDraft × members(M), SetChatMessageBudget(M)]                                            (system, coalesced)
follow-up  : [user done, CreateChatMessage(M2, replyTo user, answerJson), SaveProposalDraft(card → M2), SetChatMessageBudget(M2),
              SaveProposalDraft × remaining members(M1), SetChatMessageBudget(M1, departed ∪ {card})]                (system)
confirm    : flush coalesced job, then [...card.draftOps, ResolveProposal(card, confirmed, outcome),
              SaveProposalDraft × siblings(M), SetChatMessageBudget(M, clearAnswer if no card left pending)]       (proposal:<card>)
discard    : flush, then [ResolveProposal(card, discarded, discarded), SaveProposalDraft × siblings(M), SetChatMessageBudget(M, …)] (system)
rebuild    : [CreateChatMessage(M′, replyTo null, note text, answerJson), SaveProposalDraft(card → M′), SetChatMessageBudget(M′),
              SaveProposalDraft × remaining members(M), SetChatMessageBudget(M, departed ∪ {card})]                 (system)
undo       : applier revert (RestoreRow with expectedVersion) of the confirm/discard change set; refused if any row changed;
             on success the turn is rebuilt from the DB by the restorer (D10)
```
Every message session in a change set is written at one revision. `syncProjection` runs for every written card: a size/shape failure marks the card's "too large to sync" note (D15) but never blocks the local write.

**3.5 Restore** (`BuddyThreadRestorer`, called by `ensureRestored(gen)`, D12): pending records → distinct budget messages → for each: load the chat row and every live `ProposalRecord` by budget → `cardFromSync`/`messageFromSync` → `loader.restore` → `BuddyTurn`s keyed by user message (user row + earliest assistant reply + cards placed by origin; reply-less M′ rows attach as a note to the turn that owns their cards' origin) with `SessionMembership` from the budget's `departed`; merged into live turns by message id. Outcomes per D13. The issue type alone goes to the issue sink.

**3.6 Queue (A23b)** (`BuddyMessageQueue`, generation-scoped, started only after that generation's `ensureRestored` completes): the one dispatcher (live sends enqueue + wake); holds one timer, per-key counters and the in-flight key set; asks the controller for the next due own row; `preparedAt` + 23 h check; `WriteGate` check (D21) → `SendBuddyMessage.dispatch(snapshot)` → result as in A22 (+ D18 classes) → reschedule (D19). Lifecycle via `AppLifecycleListener` (foreground only, G2); wakes from the core reachability stream.

**3.7 Privacy** (rule 6): request/answer JSON, drafts and texts are never logged, interpolated or reported; mappers/ops/new types have content-free `toString`; the existing privacy canary test grows the restore, mapper-error, rejected-resolve, queue-failure and clear-history paths.

**Built.** Codec v2 (intent `dateHint`, card `assumed`/`removedComponents`/`adjusted`), with a full server-`Representable` sync precheck on the interpretation, draft and budget: depth, width, keys, U+0000, surrogates, raw-text decimals and duplicate members. Schema **v9**: the synced `proposals` table plus local-only `chat_messages.request_json` and `answer_json` (TD-102). The `proposal` op family has state, binding and revision guards; chat gains `SetChatMessageBudget` and `ReleaseChatMessageAnswer`. Sync mappers allowlist the proposal keys, park too-large rows and refuse unscrubbed tombstones (chat too). `ProposalRepository` returns domain `ProposalRecord`s, `resolved()` for A26. `DurableProposals` writes every card and budget through the pure `ProposalSessionWriter`. One serial `ProposalWriteLane` per thread and generation runs reply and follow-up saves, coalesced adjustment writes (flushed on dismiss, pause or before a resolve), confirm, discard, undo and restore. Confirm and discard are atomic and undoable; Undo reopens the card from the database. Follow-ups and fact rebuilds move the card to M2/M′ and rewrite the source session. Pending cards restore after the first frame, the catalog install and account recovery, once per generation. Recovery offers "Food details changed since." with Update card (offline, into M′) or Search, placeholders and orphans that can be discarded alone, the too-large note and the M′ note.

**Deviations from the plan** (details in the Progress log). Outcome `adjusted` is a stored per-card flag, not a state inspection. New engine adjustment `ProposalReidentify`: an undone card gets fresh entry IDs inside its next confirm's change set, because the old IDs are diary tombstones. Rebuilds use only the card's own meals (`ownAnswer`). Seeded random sequences replace glados for the lane property (no new dependency). Membership is thread-level. Undo reopens the in-memory pre-resolution session when the stored one can't be verified on this phone. `SaveProposalDraft.requirePending` handles the follow-up race (rec R7). Oversized local rows restore with a local-bound decode. Pending rows without refs or an origin turn become discardable orphans. D15's copy changed to "Too large to sync to your other phones. It stays on this phone.": removing an item or logging can't shrink the stored draft, so the planned advice was false.
