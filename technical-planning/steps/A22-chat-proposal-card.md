**Goal.** The most important interaction in the app: type what you ate → a proposal card appears within seconds → adjust with taps or a follow-up sentence → one tap to log. It must feel instant and never like filling in a form.

**Spec:** AI-001, AI-030, AI-031, AI-032, AI-033, AI-034, AI-035, AI-036, AI-037, AI-040, AI-041, AI-042, AI-043, AI-044, AI-140, AI-143, UX-002, UX-003, UX-011, UX-012, UX-020–026, HM-008 · **Decisions:** TD-011, D-079, D-080

## Scope
- **Input bar** (AI-001, HM-008) on Today (and Workouts in A37): focus opens the **chat bottom sheet** (UX-011) over the current screen, with the numbers behind it still visible. Pull up to full height for history, swipe down to dismiss (UX-012).
- **Send (ownership fixed 2026-10-24, A21 PA1):** A22 creates and owns the drift `chat_messages` table/migration and save-message ops through `ChangeSetApplier`; the message is saved first (full queue/retry lifecycle in A23), the **skeleton card** appears immediately (AI-030), then the interpret call runs → the ProposalEngine builds the draft → the card renders.
- **Message shape (A21 PA17/PA20):** build against B18’s contract after A21 WP4 → B18 contract commit → A22. `chat_messages` has normal metadata, role/text/status plus `codecVersion` and one bounded JSON budget field on the **assistant** row (issued question IDs/card ownership/open state/effective thresholds). User text is saved before dispatch; assistant row is the sole durable budget owner. Attachment refs/local paths are local-only, excluded from `chatMessage` sync. No per-proposal budget copies.
- **Food proposal card** (`spec/10` §4.1, UX-020): slot · time, dish name, item lines (name, amount + unit, kcal, source badge), estimate markers with a range sheet (AI-032), **assumption chips** (AI-033), **in-card questions** with answer chips (AI-034, AI-063), totals + "today after this" (AI-031), primary **Log it** and secondary **Discard**.
- **Adjusting:** tap an amount → inline number pad + unit picker (AI-040). Tap a name → up to 3 alternatives + search (AI-041). Swipe to remove, "+ add item" by text or search (AI-042). Tap slot/time (AI-043). **Follow-up typing updates the open card** (AI-044, UX-023) with the change highlighted (UX-024).
- **Confirm:** the application confirm use case composes this card’s draft ops into a `ChangeSet` with its own `Origin.proposal(card.id)` (A21 returns ops, not a ChangeSet). A23 extends this seam with resolve-proposal/status/outcome and assistant-message-budget ops in the **same transaction**; the ChangeSetApplier writes it, the card collapses to "logged ✓" + a one-line reply (AI-140, **English per AI-143**), the numbers behind animate (UX-025), haptics, undo available (AI-035).
- **Discard** (AI-037). Nothing counts until confirmed (AI-036).
- **Entry assumption display (A21 PA3, TD-084 Proposed):** map versioned `a1:` codes in `Provenance.assumptions` / `diaryEntry.assumptionsJson` to localized ARB text in `entry_details.dart` and proposal chips. Support yield, oil all/most, share, origin and fallback time/slot codes. Unknown code/version or legacy raw text → generic localized assumption, never render raw code/text verbatim. No server vocabulary validator.
- **Per-card session (A21 PA2/PA5):** one card per meal, lifecycle active/confirmed/discarded; preview = confirmed intake + only this card’s active lines, never sibling drafts. Follow-up uses `ProposalEngine.rebuild(previousCard, newRequest)` and its typed diff, retains compatible IDs/adjustments and counts carried open questions in the follow-up assistant message’s single budget. `originMessageId` never changes; `budgetMessageId` moves to the current assistant message. Restore loads the message + cards by `budgetMessageId`; the ChangeSet updates card + message together.
- Reply templates in ARB (EN), checked against the SF-020 banned words.

### 1. Summary
After A22a, the Today input bar opens Buddy's chat sheet over Today. A typed message is saved to the new synced `chat_messages` table **before** the interpret call (only through `ChangeSetApplier`), a skeleton card shows at once, and the B08 response goes through A21's read-only loader and `ProposalEngine` into one food card per meal: items with source badges, `~` estimates with their range, assumption chips and in-card question chips that recompute instantly, totals and "today after this". **Log it** applies only that card's draft ops as one `ChangeSet` with `Origin.proposal(card.id)` and collapses it to "Logged ✓ …" with one Undo, haptics and the Today number animating. Discard writes nothing. Stored `a1:` assumption codes show as localized text in cards and in diary item details. The assistant row stores the one shared question budget. App-built interpret requests become a shared corpus that the server validates. After A22b, every line can be adjusted on the card (amount pad + unit, swap from ≤3 alternatives or search, swipe remove, add, slot/time). A typed follow-up sends a bounded summary of the open card, and the full updated meal comes back and is applied with A21's `rebuild`, with the change highlighted. Pending cards survive dismissing the sheet, but not an app restart: durable proposals, history scrollback, queue/retry and the full failure UX stay A23's (TD-083).

### 3. Design

**Layers and boundaries** (`03` §2–3, enforced by `app_check`). Presentation (`features/buddy/presentation/`): sheet, composer, message list, cards; reads Riverpod state, calls application commands, never drift/dio. Application (`features/buddy/application/`): `BuddyThreadController` (keepAlive Notifier), `SendBuddyMessage`, `ConfirmProposalCard`/`DiscardProposalCard`, `ProposalPersistenceContributor` + provider, `FoodCardView`, `BuddyReplyTexts`. Data (`features/buddy/data/`): `ChatMessageOpHandler`, `chat_message_mappers.dart` (row ↔ `ChatMessage`, row ↔ `chatMessage` v1 payload, `num` → `int`), `ChatMessageRepository` (watch by IDs), `BuddyApi` (generated `BuddyClient.interpretMessage` with the 45 s receive timeout, `FailureMapper` → a closed `BuddySendFailure` class set, no logging), `InterpretRequestBuilder` (D10, one `readSnapshot`; A22b adds `activeCard`), and A21's `ProposalInputLoader` (+ `refreshContext`, + `proposalFoodOf(FoodSearchRow)` in A22b). Domain (`fb_domain`): `lib/src/chat/` (`ChatMessageDraft`, ops, `ChatText`, `ChatLanguage`), `proposals/assumption_code.dart`, exported; A22b adds `ProposalLine.alternatives`. Today imports only the buddy barrel (`showBuddySheet`); diary imports `core/l10n/assumption_labels.dart`. No new route (no `app_router.dart` change).

**Send flow (A22a)**
```
Send tap → sanitize → apply ChangeSet[CreateChatMessage(user, queued)] (direct) ─ committed
        → skeleton card in thread
        → InterpretRequestBuilder (≤100 ms) → BuddyApi.interpret(requestId = user id, receive 45 s)
        ├ 200 → loader.load(json, messageId = new assistant id, idSource, referenceTime)
        │       → ProposalEngine.build → apply ChangeSet[SetChatMessageStatus(user, done, lang),
        │         CreateChatMessage(assistant, done, 'en', replyTo = user, codec 1, budget),
        │         ...onReply contributors] (system) → cards render (or a D16 template)
        │   └ loader/engine/parse failure → same change set, assistant = "couldn't make a card" template
        └ failure → SetChatMessageStatus(user, failed) → per-class copy and actions (D6)
```
Loader admits only responses from our API via the generated client (A21 B1 residual-risk rule). `ProposalResult`s, requests, responses, texts, `FormatException`/deserialization messages and `Failure.fieldErrors` are never logged, interpolated or handed to the error reporter; new types have content-free `toString`.

**Confirm flow**: D12 + D25. Today updates by itself through the diary streams (`03` §2 rule 3).

**Migration** `core/db/migrations/from_<N-1>_to_<N>.dart`: `createTable(chatMessages)`, both indexes, three triggers; `schemaVersion` = N; `make db-migrations` dump + steps + `test/drift/user/generated/schema_vN.dart`.

**Contract**: A22a none (builds against `chatMessage` v1 as merged; the mapper reads exactly its ten fields; adds test data `contracts/testdata/buddy/interpret-requests.json` + format note in `contracts/testdata/README.md`). A22b: none of its own; it uses `InterpretRequest.context.activeCard` from `B09a (contract)` through the regenerated client.

**Card UI (A22a)**: header "Breakfast · 08:40" (`proposalSlotAtTime`); dish name when grouped; one line per item: name, amount + unit, kcal, `FbSourceBadge` or `FbEstimateMarker` (range from `line.range`, reason by source: reference dish typical portion / AI estimate / guessed amount → `showFbEstimateRange`); assumption chips from `line.chips` with `assumptionText`/option labels, tap → `showFbOptionSheet` → `ProposalSelect`; questions from `session.budget.questions` with a kind-based ARB question ("Was the rice weighed raw or cooked?", "Any cooking oil?", "Which maqluba?", "How much?") and `FbAnswerChip`s (default labelled, AI-034), tap → `ProposalSelect`; totals (`proposalTotalKcal`, `proposalMacrosShort`), today-after (D15); Discard / Log it disabled with a one-line reason when `!canConfirm` (`needsAmount` etc.) and while confirming. Resolved: "Logged ✓ 191 kcal · 1,240 left today" (or "… · 1,430 eaten today") + one Undo for 5 s; "Undone"; "Discarded". Multi-card replies render each card independently.
