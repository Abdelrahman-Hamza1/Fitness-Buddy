### P0. Summary and acceptance

Four controls on an account (AD-011): revoke one device or all devices, disable/enable, a Buddy daily limit override, delete. Each is an operator-only console POST that changes the account **through the owning module's public contract on the console's own `fb_admin` session** and writes its `admin.audit_log` row **in the same transaction** (B23 R#7 pattern). Revoke all, disable and delete need the account ID typed and a sign-in < 15 min old (AD-007). No contract change: `/v1` responses and problem types stay as they are; the console is outside OpenAPI.

Three design choices differ from what the B23 cross-card note assumed; each is recorded as a TD (P10: TD-121, TD-122, TD-123):
1. **Disable is a flag, not a lifecycle status.** `identity.users.disabled_at` is checked by every session and sign-in function. It is **not** a new `status`: `check_user_active` (what queue workers use) stays true, because a non-active user makes `QueueProcessor` erase all of that user's `ops` rows (B06 D4). A reversible disable must not destroy schedules.
2. **Delete runs the unchanged B06 coordinator in the `api` role, not in the console.** The console writes a deletion *intent* in Identity (and disables the account at once) in its audited transaction; an `api`-hosted runner picks the request up within seconds and runs `PostgresAccountDeletion` with an operator principal. So the console keeps only `fb_admin` (no `fb_app` password, no Identity pepper, no recovery mount). The `api` role already holds all three, so **no role gains a privilege**. The cross-card note's "recovery mount in the admin role" is not needed.
3. **A device is addressed by an account-scoped opaque key**, `left(encode(sha256(user_id ':' device_id), 'hex'), 32)`, never by its device ID (B23 rule: no device IDs in the console).

**Acceptance (the card's exit criteria, mapped)**
- e1 (works end to end, audited): admin-factory tests per control (T4–T8); the laptop browser run is a manual check after the merge (M1), like B23's M1–M4.
- e2 (401 after revoke; disabled can't sync or use Buddy; delete leaves zero rows): T2, T3, T6 against the api factory and the B06 all-schemas query extended to every module schema (T7).

### P1. Revoke devices (AD-011)

- `identity.admin_device_keys(p_user, p_now)` → `(device_key, platform, app_version, last_seen_at, active_sessions)`, newest first, max 50. Same columns as B23b's `admin_devices` plus the key.
- `identity.admin_revoke_sessions(p_user, p_device_key text NULL, p_now)` → `revoked int` (NULL key = all devices). It takes the user lifecycle lock (`hashtextextended(user, 4603912)`) **first**, then revalidates the user row (`FOR UPDATE`, `status = 'active'`) and returns `found = false` writing nothing when the account is gone or deleting **[R#2]**; otherwise it sets `revoked = true` on that user's live sessions (of that device), writes `identity.audit` `operator-revoked` (erased with the user) and returns the count. An unknown key returns 0 and the console reports "no such device".
- **Effect:** the next request with that bearer fails in `read_session` → `401 /errors/unauthorized`; `/auth/refresh` fails in `rotate_refresh` (session revoked) → 401. The app already handles that (`SessionService._recover`): a **registered** account goes to "session expired, sign in again"; a **guest** gets a new guest account (its local data stays on the phone). That's the app's existing behaviour, no app change. The console notes it next to the guest's controls.

### P2. Disable / enable

- Migration: `identity.users.disabled_at timestamptz NULL` (expand only). `CREATE OR REPLACE` with unchanged signatures, adding `AND u.disabled_at IS NULL`: `read_session`, `check_active`, `new_session` (so Google, email and link sign-ins all refuse) and `rotate_refresh`. Not `check_user_active` (see P0.1).
- `identity.admin_set_disabled(p_user, p_disabled boolean, p_now)` → `(found, status, was_disabled, revoked)`: lifecycle lock first, then `FOR UPDATE` on the user row; only for `status = 'active'`; **enable is refused inside the same function when an operator deletion intent exists** (`deletion-pending`), so the check and the write share one lock and one transaction **[R#3]**; disabling sets `disabled_at` and **revokes every session** (so enabling never brings an old session back); enabling clears it. `identity.audit` row `operator-disabled` / `operator-enabled`.
- **Refused requests:** every bearer request → `401 /errors/unauthorized`; refresh → 401; sign-in again → 401 (`new_session` returns nothing, mapped as today). Sync push/pull and `/buddy/interpret` re-check `check_active` inside their transactions under the same lock, so a request already past bearer validation when the disable commits is refused too (T3). **App reaction, no app change:** registered → "session expired"; signing in again fails with the generic sign-in error. There's **no "your account is disabled" message**: that would need a new problem type and app copy, so it goes to the backlog. **Guests:** disable can't stop a guest, the app just creates a new guest; the console says so and offers delete instead.
- Enable is refused while an operator deletion is pending (P4), in SQL under the lock (above).

### P3. Buddy daily limit override

- Usage migration: `usage.limit_overrides(user_id uuid PK, daily_calls int NOT NULL CHECK (daily_calls BETWEEN 0 AND 1000), updated_at timestamptz)`, ENABLE + FORCE RLS; `fb_app` SELECT on its own row (policy `user_isolation`), no direct write; erasure goes through `usage.erase_limit_override(p_user)` (definer, refuses unless `identity.erasure_in_progress`; security review major 1); `fb_migrator` owner policy for the definer functions. A user table in `UsageModule.UserData` (`["daily", "limit_overrides"]`), deleted by `UsageErasure`.
- `usage.admin_daily_limit(p_user)` → `int|null` and `usage.admin_set_daily_limit(p_user, p_calls int NULL, p_now)` → previous value (NULL = default; clearing deletes the row). Only `fb_admin` can run them. **[R#2]** The setter can't see Identity (module boundary), so the console handler first calls `IIdentityAdminControls.LockAsync(session, user)` (`identity.admin_lock_account`: lifecycle lock, then revalidate active and no deletion intent) in the **same** session and writes the override only when that succeeds; the lock is held until commit, so a deletion either finished before (→ refused, nothing written) or waits and then erases the override. The setter also takes the lifecycle lock itself as its first statement (re-entrant), so it never writes without it.
- `PostgresUsageRecorder.ReserveAsync` reads the caller's own override first (same transaction, RLS), so `ceiling = override ?? default`. **[R#4]** A ceiling ≤ 0 returns *not reserved* **before** the INSERT (today's first INSERT of a day is unconditional; only its `ON CONFLICT` update checks the ceiling), so a zero limit allows no physical send even on a fresh day. `0` = Buddy off for this account: `Limited` → the existing `429 /errors/rate-limited` with `Retry-After` until UTC midnight, which the app already handles. `ReserveAsync` returns the effective ceiling, so the `RateLimit-Policy` `q=` header matches the override (`IUsageRecorder` gets a small `UsageReservation(bool Reserved, int Ceiling)` result; Buddy is the only caller).
- The console sets 0–1000 or "default". No typed confirmation (not in AD-007's list).

### P4. Delete (AD-011 → AC-031's server deletion)

- **The intent lives in Identity [R#1].** `identity.operator_deletions(user_id uuid PK REFERENCES identity.users, requested_at, attempts int DEFAULT 0, available_at, last_error text NULL CHECK IN ('recovery-unavailable','unavailable','failed'))`, ENABLE + FORCE RLS (`fb_app` no direct grants, like every Identity table; `fb_migrator` owner policy). It's an Identity user table, deleted by `identity.erase_user` (`CREATE OR REPLACE`, before `users`), so no new Account table and no cross-schema SQL.
- **Functions (Identity, definer, fixed `search_path`):**
  - `admin_request_deletion(p_user, p_now)` → `(found, created)`, **`fb_admin` only**: lifecycle lock first; the user must exist with `status = 'active'`; it sets `disabled_at`, revokes every session and inserts the intent (ON CONFLICT DO NOTHING) in one statement block. It's the **only** way to create an intent: `fb_app` has no grant on the table or the function (T11 negative tests).
  - `admin_deletion_state(p_user)` → `(requested_at, attempts, last_error)`, `fb_admin`.
  - `due_operator_deletion(p_now)` → one `user_id` or none (ids only, like queue discovery), `fb_app`.
  - `begin_operator_deletion(p_user, p_now)` → `boolean`, `fb_app`: requires `app.user_id = p_user`, takes the lifecycle lock, then locks the intent row `FOR UPDATE` and requires it **committed and due** (`available_at <= p_now`) and the user `status = 'active'`; otherwise returns false and changes nothing (no status, no session change). Only then `status = 'deleting'`, sessions revoked, `identity.audit` `deletion-pending`. So a direct `fb_app` call without an operator intent can't delete anything (T11).
  - `record_operator_deletion_failure(p_user, p_code, p_now)` → `boolean`, `fb_app`: `app.user_id = p_user`, lifecycle lock, then `UPDATE … WHERE user_id = p_user` only if the intent still exists (attempts + 1, backoff `min(2^attempts, 60)` min, closed code). Zero rows when the deletion committed, so it never recreates anything.
- **Lock order everywhere [R#2]:** recovery (coordinator only) → user lifecycle → user/intent rows. Console transactions never take the recovery lock and take the lifecycle lock as the first statement of their first Identity call, so no path waits for recovery while holding a lifecycle lock.
- **Console transaction** (`fb_admin`): typed ID + recent sign-in checked → `IIdentityAdminControls.RequestDeletionAsync(session, user)` (disable + revoke + intent, under the lock) → audit `accounts/delete-requested` → commit. The account stops working at once.
- **Runner [R#5]** (`OperatorDeletionRunner`, Account Infrastructure, a `BackgroundService` registered only by `ApiRole`, poll 5 s, off in `Testing` unless a test turns it on). Per tick, at most 10 items: `IIdentityOperatorDeletions.DueAsync` → `IAccountDeletion.DeleteForOperatorAsync(user)`. The coordinator is the **same** method refactored to one core with two principal checks: the app path keeps `CheckActiveAsync(session, user, sessionId)` + `begin_deletion`; the operator path calls `BeginOperatorAsync` (`begin_operator_deletion`), so the intent check is in the database. Everything else is unchanged: exclusive recovery lock, lifecycle lock, generation fence before any effect, `UserErasure` dispatched in the transaction, `OpsErasure`, commit, and reconciliation **only** of a known pre-commit failure (never after an ambiguous commit, B06 D7).
  - **Containment:** every item runs in its own `try`. Shutdown cancellation (`stoppingToken`) ends the loop quietly. Any other exception (participant failure, SQL, timeout, recovery, connection loss, a lost commit acknowledgement) is logged as its type and recorded with `record_operator_deletion_failure` in a new transaction (that call is itself caught and logged). Nothing escapes `ExecuteAsync`, so the API never stops because of the runner; the tick loop has its own outer catch with a 30 s delay.
  - **No false completion:** the runner never marks success itself; success = the intent row erased in the deletion transaction. After an ambiguous commit, the failure update hits zero rows if the commit landed. If it didn't, the intent stays and is retried, and a mismatched recovery generation fails closed (B06) until the operator's recovery runbook.
  - `Unavailable` (missing erasers) records `unavailable`; `RecoveryUnavailableException` records `recovery-unavailable`; anything else `failed`. The account stays disabled; the console shows "deletion pending, last error …, next try …". No cancel in R1.
  - **Restart / competing runners:** the intent row lock and the exclusive recovery lock serialize two runners (two `api` instances later); a restart just finds the due intent again.
- **Races [R#6]:** app deletion **first** → the user is gone, the console's request returns `found = false` (refused, audited). Operator request **first** → sessions are revoked, so the app's `DELETE /v1/me` gets 401 (`CheckActiveAsync` false) and the runner completes the erasure.
- **Zero rows:** the B06 query (`AssertNoOwnerRows`) is extended from `identity/account/userdata/ops` to **every module schema** (`usage`, `buddy`, `catalog` too) and run after an operator deletion of a seeded account that has data in each (T7).
- **What the device keeps:** like any server-side deletion it can't wipe the phone. The next request gets 401. A registered user who signs in again gets a **new** account; a guest's app creates a new guest. The runbook says so.

### P5. Audit rows for a deleted account (cross-card decision)

- Rows keep `target = "account <uuid>"`; the log stays append-only, with no edit path and no retention job. After deletion the ID maps to no row in any schema, so it is a pseudonymous reference to nobody. B06 D6's "no durable user mapping" covers user-data tables, and this log holds none.
- **Rule:** account-control rows never contain an email (not even masked), a device ID, a Google subject or user content. `before`/`after` hold only codes and numbers: `{"disabled":false}`, `{"revoked":2}`, `{"dailyCalls":null}` → `{"dailyCalls":0}`, the device key, `{"deletion":"requested"}`. **[R#7]** Account controls take **no free text**: the reason is a closed code (`owner-request`, `test-account`, `security`, `abuse`, `support`, `other`), validated server-side and stored in `reason`. So no email or content can enter an account row.
- **Display:** the audit window shows the ID as is. The account page for an ID that no longer exists says "no such account (deleted or never existed)", so a deleted account and a typo look the same.
- Documented in `docs/runbooks/admin-console.md`, `04` §6 (elevated paths) and as a TD. The B23 card's note is closed.

### P6. Console UI and endpoints

All under `/admin/accounts/{id}` (route ID = the operator's target, a canonical UUID; it is never a user's own scope). The markup stays **separable** from B23b: one `AccountControls.razor` component plus its endpoints in `AccountControlEndpoints.cs`. Until B23b lands it renders on its own page `GET /admin/accounts/{id}/controls`; after the rebase, B23b's account page includes the component with one line, and the device list there gets the revoke buttons.

| Endpoint | Capability | Extra |
|---|---|---|
| `GET /admin/accounts/{id}/controls` | Session | viewers see state, no forms |
| `POST …/devices/{key}/revoke` | Operate | key `^[0-9a-f]{32}$` |
| `POST …/revoke-all` | Operate | typed ID + recent sign-in (checked in the handler, audited) |
| `POST …/disable` | Operate | typed ID + recent sign-in (checked in the handler, audited) |
| `POST …/enable` | Operate | refused while a deletion is pending |
| `POST …/buddy-limit` | Operate | `0–1000` or empty = default |
| `POST …/delete` | Operate | typed ID + recent sign-in (checked in the handler, audited) |

- Plain forms (antiforgery, same-origin guard from B23), redirect-after-POST with a notice; status shown as icon + word (AD-008); no htmx needed.
- **Handlers** (Application, one per use case): `ReadAccountControls`, `RevokeDevice`, `RevokeAllDevices`, `SetAccountDisabled`, `SetBuddyLimit`, `RequestAccountDeletion`. Each opens one `fb_admin` session, calls the module contract, writes the audit row, commits. A refusal (wrong typed ID, stale sign-in, unknown account or device, not active, deletion pending) changes nothing and is audited as `refused` with a reason code in its own transaction (B23 pattern). Every mutating handler's first module call takes the lifecycle lock and revalidates the account (P4 lock order) **[R#2]**. The handlers re-check typed ID and recent sign-in themselves too (defence in depth behind the filter).
- **Typed ID** (Domain, pure): trimmed, case-insensitive canonical UUID equal to the route ID.
- **New public contracts:** Identity `IIdentityAdminControls` (`StateAsync` incl. deletion state, `DevicesAsync`, `LockAsync(session, user)`, `RevokeAsync(session, user, key?)`, `SetDisabledAsync(session, user, bool)`, `RequestDeletionAsync(session, user)`) and `IIdentityOperatorDeletions` (`DueAsync`, `RecordFailureAsync`, used by Account's runner); `IIdentityDeletion.BeginOperatorAsync`; Usage `IUsageAdminControls` (`DailyLimitAsync`, `SetDailyLimitAsync(session, …)`). No new Account contract. Mutating methods take the caller's `DatabaseSession` (B23 R#7). Implementations stay `internal`.
- **Logs:** `[LoggerMessage]` with the audit ID, the action code and the outcome only. Never the account ID together with anything else, never the typed text, never the reason.

| Risk | Mitigation |
|---|---|
| Disable leaves a gate open | One flag checked in all four session/sign-in functions plus in-transaction `check_active`; T3 covers bearer, refresh, both sign-ins, sync, Buddy and the in-flight race |

| The runner stops the API | Per-item and per-tick catches; failures recorded only while the intent exists (T7) |

| Request stuck when recovery is broken | Account stays disabled (safe), error code visible, retry with backoff; recovery repair is the existing runbook |

| B23b conflict | Own files and routes; one include line at the rebase |

### P10. Technical decisions (recorded as TD-121–TD-123)
- **TD-121 (recorded) Operator account controls:** disable = `identity.users.disabled_at`, checked in the session and sign-in functions and in `check_active`, never a lifecycle status; revocation per device through an account-scoped opaque key; every control is a module-owned `admin_*` definer function on the console's session, audited in the same transaction.
- **TD-122 (recorded) Operator deletion:** the console writes an Identity-owned intent (only `fb_admin` can) and disables the account in one audited transaction; an `api`-hosted runner runs the unchanged B06 coordinator with an operator principal whose database capability requires that committed, due intent under the lifecycle lock; the console never holds `fb_app`, the pepper or the recovery mount. It amends the B23 cross-card note.
- **TD-123 (recorded) Audit rows after deletion:** keep the pseudonymous account ID; no emails, device IDs or content in account-control rows, and reason codes instead of free text; no retention job; "no such account" display.

### P11. Owner items
None expected. Every choice keeps or narrows privileges, and the spec is unchanged. To report (not gates): there's no "account disabled" message in the app (backlog), and disable/revoke can't stop a guest re-creating itself.
