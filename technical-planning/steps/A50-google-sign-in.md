## Low-level plan
_Written in Phase B (2026-10-30, `step-planner`, lane 3, branch `step/A50-google-sign-in` from `origin/main` 54daffa). **Tier: Risky** (sign-in) → own Codex plan review, then two Codex review tasks (code/architecture + security/data integrity). ### 1. Summary
After A50 a release build with the web/server client ID compiled in shows **Continue with Google** and gets a real Google ID token through `google_sign_in` 7.x (Credential Manager on Android). The token goes through A33's existing flows unchanged: guest upgrade (`linkIdentity`), plain sign-in, 409 merge/discard, session expiry. Plugin errors map onto A33's fixed sign-in failures. Builds without the ID (dev, debug, Patrol, CI without the optional secret) keep `UnconfiguredGoogleIdTokenSource` (button hidden). Tests use fakes; the real plugin is checked only by the owner on the A55.

| D4 | **Client ID delivery follows A11 D13 (the `FB_API_BASE_URL` convention): a new define `FB_GOOGLE_SERVER_CLIENT_ID`.** Committed `config/{dev,staging,prod}.json` hold `""` (Google off). **The ID goes only into release builds signed with the release key (PA2).** `build-android.sh` decides this after `load_release_env`, once both `MODE` and the signing outcome are known. Added to `AppConfig.keys`, so the existing "every config file has exactly these keys" test covers the three JSON files. | Same fail-closed pattern as the other defines. No I/O, safe before the first frame (UX-001). |
| D6 | **Adapter `PluginGoogleIdTokenSource`** in `core/account/google_plugin_id_token_source.dart`, the only file that imports the plugin. It sits on a three-method seam `GoogleSignInDriver { Future<void> ensureInitialized(); Future<String?> authenticate(); Future<void> signOut(); }`. **The production `PluginGoogleSignInDriver` keeps one process-wide initialization future** (a `static` / top-level `Future<void>?`, so even a second driver instance can't call `GoogleSignIn.instance.initialize` again): created on the first `ensureInitialized()`, shared by every concurrent and later caller. **A failed initialization is kept**: never reset, never retried in this process, because calling `initialize()` twice is undefined in 7.2.0 (PA1). Callers see it as a redacted `GoogleIdTokenException(unavailable)` (or `misconfigured` for `clientConfigurationError`). Google stays unusable until the app restarts. `isAvailable` = a non-empty ID **and** `defaultTargetPlatform == android` (iOS needs its own client and URL scheme: R2, D-081). Initialization runs **lazily on the first `idToken()`**; nothing runs at startup. | The singleton must be initialized exactly once (`google_sign_in` 7.2.0 source/docs). A seam keeps the error mapping, the single shared init and sign-out behaviour unit-testable with real `GoogleSignInException` values. Local-first startup (rule 3). |
| D7 | **Error mapping.** The adapter returns `null` for a cancel and throws a redacted `GoogleIdTokenException(GoogleIdTokenFailure kind)` (declared next to the interface; `toString` shows the kind only, never the plugin description). `SignInFlow.signInWithGoogle` maps it onto A33's `AccountFailureKind`. See the table below. | A33's sign-in states are reused. Only the "unavailable" message is new (one ARB string) because it gives the user a next step (email). |
| D8 | **Sign-out is best effort and bounded.** The adapter's `signOut()` is a no-op if initialization was never started, **still pending, or failed**: it never touches the singleton before a successful init and never waits for a pending one. Otherwise it calls `driver.signOut()`. The **whole** call, every wait included, sits inside one **5 s timeout** and swallows every error. `AccountService.signOut` also wraps `_google.signOut()` in `try/catch` (defence in depth), so a plugin fault can never block AC-004. | A33 awaits `_google.signOut()` **before** the sign-out transition: a hang or throw there would stop sign-out. A pending init means no Google account was chosen in this process, so there's nothing to clear. |
| D9 | **Privacy.** We never read `account.email`, `displayName` or `photoUrl`. The ID token stays inside `SignInFlow` memory (A33 §6). No log, breadcrumb or exception text carries the token or the plugin description. The adapter catches everything, so no plugin `PlatformException` reaches Sentry's unhandled-error hook. | Rule 6, `09` §4, A33 D10. |

**D7 mapping:**

| Plugin outcome (`GoogleSignInExceptionCode` / other) | Adapter | User-facing (`AccountFailureKind` → text) |
|---|---|---|
| `canceled` (picker closed; per the README this can also hide a config error) | `null` | `AccountOutcome.cancelled`: stays on the screen, no message |
| `providerConfigurationError` (no Google Play services / Credential Manager provider, unsupported), `MissingPluginException` | `unavailable` | `googleUnavailable` → **new** `signInErrorGoogleUnavailable` ("Google sign-in isn't available on this phone. Use your email instead.") |
| `clientConfigurationError` (missing/wrong `serverClientId`), success with a `null` ID token | `misconfigured` | `googleUnavailable` → same text |
| `interrupted`, `uiUnavailable`, `userMismatch`, `unknownError` (also no account on the device, and network failures inside Google's sheet: the plugin has no network code), any other `PlatformException`/error | `failed` | `rejected` → existing `signInErrorOther` ("Couldn't sign in. Try again.") |
| Our API call after the token (no connection / 5xx / 409 / 4xx) | n/a | unchanged A33 mapping (`offline`, conflict sheet, `rejected`) |

### 3. Design
- **`google_id_token_source.dart`** (existing): update the doc comments (`idToken()` returns `null` on cancel and throws `GoogleIdTokenException` on failure). Add `enum GoogleIdTokenFailure { unavailable, misconfigured, failed }` and `final class GoogleIdTokenException implements Exception` with a kind-only `toString`. `UnconfiguredGoogleIdTokenSource` is unchanged.
- **`google_plugin_id_token_source.dart`** (new): `GoogleSignInDriver` (interface), `PluginGoogleSignInDriver(serverClientId)` (wraps `GoogleSignIn.instance`: `ensureInitialized()` over one process-wide, kept `initialize(serverClientId:)` future (PA1), `authenticate()` → `account.authentication.idToken`, `signOut()`), and `PluginGoogleIdTokenSource({required String serverClientId, GoogleSignInDriver? driver, TargetPlatform Function()? platform, Duration signOutTimeout})`.
- **`account_providers.dart`**: `googleIdTokenSource` watches `appConfigProvider` and returns `PluginGoogleIdTokenSource` when the ID is set and the platform is Android, else `const UnconfiguredGoogleIdTokenSource()`. Regenerate `.g.dart` (codegen only).
- **`account_service.dart`**: `signInWithGoogle` catches `GoogleIdTokenException` → `AccountFailure` (D7). Before any server call, so a failure changes nothing: no registry write, no session accept, guest untouched (AC-002). `AccountFailureKind.rejected`'s doc becomes "the server or Google refused". `signOut` guards `_google.signOut()` (D8).
- **`sign_in_screen.dart`**: `googleUnavailable` → `l10n.signInErrorGoogleUnavailable`. The error currently renders under the email field: keep that position (no layout change). **ARB**: one new key in `app_en.arb` with a description.
- **Config/build**: `app_config.dart` (field, key, validation); `config/*.json` (+ `"FB_GOOGLE_SERVER_CLIENT_ID": ""`); `tools/scripts/android-defines.py` (env > private file > placeholder, regex, no echo); `build-android.sh` header comment; `build-android-selftest.sh` (env override, file fallback via a temp `FB_GOOGLE_CLIENTS_FILE`, malformed rejected, canary never printed; it must point `FB_GOOGLE_CLIENTS_FILE` at a fixture so it never reads the real laptop file); `ci.yml` build step env `FB_GOOGLE_SERVER_CLIENT_ID: ${{ secrets.FB_GOOGLE_SERVER_CLIENT_ID }}` (empty when unset → Google hidden; update `test_android_ci.py` if it pins the env list); `Makefile` `build-android` help text.
- **Runbooks**: `android-signing.md` §3 secrets table (+ optional `FB_GOOGLE_SERVER_CLIENT_ID` = the `WebClientId`) and the A11 section; `identity.md` (the app integration is A50; laptop builds read `google-clients.json`); `install-a-build.md` (one line: Google needs a laptop USB build, or a CI build with the secret).
- **Android**: no manifest or Gradle change expected. The plugin brings `androidx.credentials` + `googleid` with their own consumer R8 rules; `minSdk` 26 is fine. `apk_hardening_check.py` has no permission allow-list, and the plugin adds no permission.
- **Rules respected**: no new API types (the existing generated `GoogleSignInRequest`/`LinkIdentityRequest`); no user-data write path (A33's `AccountTransitions` is unchanged); no network or plugin init on the startup path; the plugin is confined to one file behind a port (`03` layering: `core/account` adapter, feature code sees only `AccountService`).

### 7. Risks & unknowns
- **R1: the Android OAuth client may not match the build** (package or SHA-1). It was registered on 2026-10-18 with the release certificate, but the repo doesn't record **which package** (prod `io.github.abdelrahmanhamza1.fitnessbuddy` vs `.staging`). Symptom: `clientConfigurationError`, or a `canceled` right after choosing the account (README caveat) → "unavailable" or a silent return. Handling: the owner check uses **prod**, the most likely registration. Staging also gets the ID (D4): if staging fails, that's recorded and not fixed here. A real mismatch needs a Cloud Console edit, which becomes an owner item in a follow-up, outside this step's "no Console work" scope. Debug and `.dev` builds never get the ID, so they can't show a failing button.
- **R2: no Google Play services** (or a missing Credential Manager provider) → `providerConfigurationError` → the "use your email" message. The email path is unaffected (T9). The A55 has Play services, so there's no device risk for R1.
- **R3: R8 stripping Credential Manager classes in release** ("no provider dependencies found" at runtime). **Implementation check in WP2 (PA3):** after `pub get` and one release build (through `heavy.sh`), inspect the resolved AARs' consumer ProGuard files (`androidx.credentials:credentials-play-services-auth`, `credentials`, `googleid`, in the Gradle cache or `build/intermediates`) and the merged release R8 configuration (`-printconfiguration` or `build/outputs/mapping/<flavor>Release/configuration.txt`). Confirm the keep rules for `androidx.credentials.playservices.**` and the `googleid` classes are present. Add an explicit keep rule in `android/app/proguard-rules.pro` (and wire it in Gradle) **only if** they're missing; the evidence goes in the Progress log. Real provider execution stays the optional A55 check: CI's `android-it` runs debug.
- **R4: the singleton's "initialize exactly once"**: one process-wide shared future in the production driver, failures kept and never retried (D6, PA1, T2). The provider is also `keepAlive`. A one-off init failure makes Google unavailable until the app restarts; that's acceptable, and email still works.
- **R5: re-using one Google token for the conflict follow-up** (A33 `chooseOnConflict` re-sends the pending token to `/auth/google`). Fine today: B04 verifies the signature, aud, iss and exp, with no single-use cache, and the token lives for about 1 h. If the server ever adds replay protection, the merge/discard path must fetch a fresh token. Noted only.
- **R6: Patrol budget**: one more app boot (about 1 min) in the 25-minute `android-it`. A journey that has never run on the emulator may need a fix round (PROCESS owner rules).
- **R7: CI-built APKs have no Google** until the owner adds the optional `FB_GOOGLE_SERVER_CLIENT_ID` secret. Not a regression (Google is hidden today). The owner installs over USB (laptop builds have it).
- **Card doubts:** the card's **Decisions** line cited **TD-006** (sync); corrected to **TD-024** (own Identity module) in plan-review round 1. D-087 isn't on `main` yet (it's in a pending group merge).
- **Open research questions:** none blocking. Whether `google_sign_in` 7.2.x Android reports a network failure as `unknownError` or `noCredential` is only cosmetic (both → "Try again").

### Plan-review amendments (Codex round 1, 2026-10-30: changes requested, 2 majors + 2 minors)

- **PA2 (major):** the client ID goes only into release builds signed with the release key, decided after signing is resolved in `build-android.sh`; self-test cases for staging/prod `MODE=debug` and a debug-key release build without the ID. Changed D4, T11.
- **PA3 (minor):** WP2 checks the resolved AAR consumer ProGuard rules and the merged release R8 config; explicit keep rules only if missing. Changed R3.
- **PA4 (minor):** card Decisions line TD-006 → TD-024.
