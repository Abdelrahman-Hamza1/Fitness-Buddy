_New step (orchestrator, 2026-10-23, A09 plan review PA3; semantic validation added at re-check 1, F1). The app side is A09a; the upload is A34's._

**Goal.** The server stores, validates, serves and erases the new `personalFood` sync entity exactly as the contract says, so A34 can upload personal foods.

**Spec:** FD-071 (private personal foods), AC-010 (foods sync to the account), AC-012 (offline changes sync; row-level last-write-wins + history, `05` §5), AC-031 (deletion covers them) · **Decisions:** TD-031, TD-049, TD-061

## Scope
- **Starts from A09a WP1's contract commit** on `main`: `personalFood` v1 in `contracts/openapi/sync-entities.json`, its fixture in `contracts/testdata/sync/entity-payloads.json`, and the regenerated embedded `backend/src/Modules/UserData/Infrastructure/Schemas/entities.json`. B17 doesn't change the contract; a needed change goes back to the app track as a contract commit first (breaking → owner).
- **Semantic validation (F1):** the schema checks only what the exporter can express (types, enums, number bounds, `maxLength`), and `SyncPayloads` checks `...Json` strings only for representability. B17 adds a `personalFood` validator in the UserData module that enforces **every rule of the A09 card's §3.0 table** ("Shared `personalFood` rules"), the same numbers as the app's `PersonalFoodBounds`: names and brand 1–80 / 1–60 characters after trimming; `aliasesJson` a list of ≤ 30 strings of 1–80 characters, no exact duplicates; `barcodesJson` ≤ 10 unique GTIN-8/12/13/14 strings with valid check digits; `per100ExtrasJson` keys from the `NutrientKey` codes, gram values 0–1,000, mg values 0–100,000; `servingsJson` ≤ 10 `{unit, amount}` with units from the closed vocabulary, unique, amounts 0.1–5,000; `entryServingUnit` and `entryServingAmount` both null or both set (amount 0.1–5,000); `createdFrom` 1–32 letters; every number finite. A failure is a per-change `invalidPayload` with no value echoed. The validator's constants are pinned to the generated corpus constants block, sourced from the app's `PersonalFoodBounds` for §3.0; a separate table check confirms every field row exists (PA8). The FD-012 sanity check stays app-side: a food saved with a warning must sync.
- **String/JSON parity (A09a security round 1):** all string-length limits count **UTF-16 code units**, matching Dart `String.length` and .NET `string.Length` (not Unicode code points). Trimming must equal Dart `String.trim()` exactly; do not assume the platform's default trim has the same whitespace set. Pin Unicode whitespace and supplementary-character boundary cases against the app. Reject duplicate JSON object keys before materializing objects, including inside JSON-string payload fields, so a parser cannot silently select a conflicting value. **Sanity is not a sync rule**: wire-valid values remain syncable even when the app-only check reports `macrosTooHeavy` or another hard sanity failure; sanity constrains new app input, not stored-row reads, metadata updates or merges.
- **Conformance:** push accepts a valid `personalFood` v1 document from its owner; each §3.0 rule and each schema rule (unknown `state`/`basis`, over-long strings, extra or missing fields) has a rejection case.
- **Behaviour:** pull, LWW with history (`row_history`, 30 days), tombstones and compaction fences, guest 403, RLS (another user can't read it), item history `GET /v1/sync/history/personalFood/{id}`: the existing generic paths, proven for this entity.
- **Erasure:** B06's account deletion removes `personalFood` documents, history and fences (the "no rows remain" test includes it).
- **Telemetry:** metrics and logs carry no names, aliases, barcodes or values (the B05 canary pattern).
- **Shared corpus and app parity (PA2/PA3, explicitly assigned to Codex for B17 under TD-078):** add the fb_domain generator and byte-equality drift test, shared vectors, and an app mapper test in `apps/mobile/test/features/foods/data/`. The actual `personalFoodOf` decoder and `personalFoodColumns` writer prove both directions; no app production-code change.
- A fresh read-only Codex **security review** of the diff (authorization/RLS, input handling, logging), findings fixed and recorded.

### Design and decisions

- **D1 · Entity-specific admission hook.** Add internal `PersonalFoodPayloadValidator` and `PersonalFoodBounds` in UserData Infrastructure, alongside `SyncPayloads`. Keep `SyncPayloads.InvalidReason(SyncVersion)` as the admission entry point. First run the existing registry/schema and representability checks (including duplicate keys), then dispatch only `personalFood` schema 1 to semantic validation. Reuse the existing bounded nested-JSON parsing pass: validate each parsed `...Json` value before disposing its `JsonDocument`, rather than decoding the same string twice. The validator returns a boolean; the caller exposes only `invalidPayload`. No exception text or failing field value leaves it. Preserve `unsupported` for unknown entity/version, existing `mealSlot` semantics and the other entities' behavior. `PostgresSyncStore.PushForSessionAsync` is the production path; its internal `PushAsync` deliberately skips payload admission and cannot prove validator acceptance/rejection.
- **D2 · Contract and shared constants.** A09a already delivered the contract, embedded registry and valid fixture. Consume them unchanged; keep the exporter closed and rejecting `description`. `contracts/README.md` continues to point to A09 §3.0. Constants are name/alias 80, brand 60, aliases 30, barcodes 10, servings 10, kcal 920, gram nutrients 1,000, mg nutrients 100,000, serving min/max 0.1/5,000, creation code 32, JSON-string length 16,384; minima for non-null text are 1 and numeric nutrients 0. The generated corpus `constants` block is the machine source for C# constant parity assertions (PA8), sourced from `PersonalFoodBounds`; compare the schema's expressible bounds too. The §3.0 Markdown check confirms **every field row exists**, without parsing numbers from prose. Pin server extras/units/state vocabularies to corpus blocks generated from `NutrientKey.values` (including units), `PersonalFoodBounds.units` and `FoodState.values`. Document server-first vocabulary evolution in `contracts/README.md` and proposed TD-080 (PA4), extending TD-031's validation clause without changing it. These are build/test inputs; deployed validation uses compiled constants and the embedded registry, with no runtime file/contract fetch.
- **D3 · Exact string and GTIN behavior.** Count UTF-16 code units with `string.Length`, including supplementary characters. Implement a fixed C# switch over the exact Dart-trim set emitted by scanning all 65,536 BMP code units except surrogates with the pinned SDK. The expected set is U+0009–000D, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F, U+3000 and U+FEFF. U+0085 is trimmed on both platforms; U+FEFF is the known Dart-only point. Compare `char.IsWhiteSpace` over the same scan, including U+001C–001F, and pin actual differences rather than assuming them (PA5). Do not use platform-default trim. Validate names, nullable Arabic name/brand and aliases after that trim; aliases are unique with ordinal equality **after trimming**, matching the draft constructor and `validateWire()`. No case folding or `normalizeKey` in server admission. Null optional values and correctly typed empty lists/objects are allowed; inner JSON text `"null"` and wrong-root strings/numbers are rejected, since the app writes SQL null (PA7); non-null blank names/brand/aliases are not. Schema raw-string `maxLength` still applies before semantic trimming, as it does on the wire; do not rewrite the payload or its fingerprint. GTINs remain untrimmed digit strings, preserving leading zeroes; accept exactly 8/12/13/14 ASCII digits, ordinal unique, and compute the same alternating 3/1 checksum as `Gtin.isValid`. Creation codes are 1–32 ASCII letters without trimming; use a bounded character loop, not a regex. Reject ill-formed UTF-16, including lone high/low surrogates in `nameEn` and decoded aliases, with `invalidPayload`, never a 500 (PA6). App `validateWire()` hardening remains Claude's backlog; do not change it here. No new regex is needed anywhere.
- **D4 · Numbers, closed vocabularies and stored-row parity.** Retain `SyncPayloads.Representable`'s finite, exact .NET-decimal representation checks before comparing decimal bounds, including inside JSON strings. Reject overflow, underflow/rounding and oversized numeric tokens rather than converting via `double`. `per100ExtrasJson` must be an object: gram keys `sugar`, `saturated_fat`, `trans_fat`, `alcohol`; mg keys `sodium`, `cholesterol`; all values numbers in their respective bounds. `servingsJson` must be an array of at most ten objects with exactly `unit` and `amount`, no missing/extra keys; units unique and from `piece`, `loaf`, `plate`, `glass`, `sandwich`, `disc`, `serving`, `can`, `cup`, `tbsp`, `tsp`. Entry unit/amount are both null or both present with the same vocabulary/amount bounds, independently of the servings list. State/basis use the contract enums. Do not require an entry serving to occur in the list. The compatibility oracle is the real `personalFoodOf` row decoder, with `personalFoodColumns` for the writer direction (PA2). Domain `validateWire()` and `Gtin` supply bounds/checksum reference behavior, while `validate()` adds form-only sanity: accept kcal mismatch and wire-valid `macrosTooHeavy` rows, so metadata edits/merges and warning-accepted foods sync without recomputation.
- **D5 · Bounded hostile-input handling.** Keep raw `JsonElement` until duplicate-key detection, including escaped spellings of the same decoded property name and keys inside all JSON-string fields. Never first deserialize to a dictionary that loses duplicates. Check the schema's 16,384 UTF-16-unit string cap before nested parsing; retain depth 24, object-property 128 and array 500 generic representability limits, then enforce the smaller entity counts. Use ordinal sets and single bounded passes, fixed vocabulary lookups and GTIN loops of at most 14 digits. Work is linear in bounded input size; do not use normalization, backtracking regexes or repeated concatenation. Keep host 256 KiB/500-change limits and existing fixed envelope errors: syntactically unreadable outer JSON (including bare NaN/Infinity) is 400; representable envelopes with semantically invalid payloads are per-change `invalidPayload`; actual host body overflow is 413. Malformed inner JSON, quoted non-finite values and numeric overflow are per-change failures. Invalid items cannot enter documents, history or receipts, and a valid neighbor in the batch still succeeds. Envelope-level duplicate `entity`/`payload` properties are a separate STJ last-wins issue: the WP4 security review decides whether to enable .NET 10 `JsonSerializerOptions.AllowDuplicateProperties = false`, with API regression tests if adopted; otherwise record a concrete backlog item and disposition (PA11). Payload/inner-object duplicate rejection remains mandatory either way.
- **D6 · Existing storage, isolation, retention and erasure.** Keep one document per row and the existing authenticated API, advisory lock/live-session checks, forced RLS and module eraser. No new table, endpoint, DTO, schema version, SQL capability or erasure participant. Prove this entity follows LWW, immutable replay, stale/displaced history, tombstones and 30-day retention/compaction based on server acceptance. Client tombstones carry full payloads and receive identical schema/semantic validation to live versions; corpus cases pin both (PA7). Compacted `{}` payloads are server-produced deletion fences, never accepted as client live or tombstone payloads. B06's `UserDataErasure` already removes documents/fences, row history and version receipts without filtering entity; extend its real account-deletion test with live, historical and compacted personal foods, retaining a second owner's controls.
- **D7 · Privacy boundary.** Push acknowledgements, rejection/problem responses and forbidden/other-user responses contain no names, aliases, brand, barcodes, nutrient/serving values or validator details. Authorized owner pull/history necessarily return the stored payload under the existing contract; this is the only intended response disclosure. No user content goes to logs, spans/events/status, metrics or serialized Sentry envelopes, including errors and successful owner reads. Extend B05's actual traffic/canary capture across accepted and rejected personal foods, pull/history, malformed input and injected failures; inspect Postgres logs too. Keep existing fixed operation/count/duration telemetry rather than adding labels from payloads.
