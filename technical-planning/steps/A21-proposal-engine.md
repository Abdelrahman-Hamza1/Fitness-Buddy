**Goal.** The deterministic heart of Buddy on the phone: turn an interpretation into a proposal draft (numbers, assumption chips, at most two questions, "today after this") and recompute instantly on every tap, with no network and no AI cost.

**Spec:** AI-015 (per-meal cards), AI-044 (follow-up seam), AI-020, AI-021, AI-022, AI-023, AI-031, AI-032, AI-033, AI-034, AI-040–043 (recompute side), AI-060, AI-061, AI-062, AI-063, AI-064, AI-101 (shares), FD-060, FD-061, FD-062, D-072, AQ-04, AQ-05, AQ-06, AQ-07, AQ-08, AQ-10 · **Decisions:** TD-009, TD-081–TD-084 (Proposed)

## Scope
- **`ProposalEngine`** in `fb_domain` (`06` §3.3):
  1. Resolve each dimension: stated → saved default (memory, from A26. Empty for now) → question candidate.
  2. Compute kcal per option. **Ask only if** the options differ by > 20% **and** > 50 kcal (thresholds from `/v1/config`). Keep **≤ 2 questions**, ranked by kcal impact. The rest become chips with defaults.
  3. Yields when the stated state ≠ the matched state, with the note.
  4. Cooking fat as its own line, the "all oil eaten" / "most oil left in the pan" chip (FD-061).
  5. Shares ("we were 6", fractions, plates).
  6. Totals (kcal, P, C, F, fiber) + **"today after this"** from local diary + targets.
  7. Estimate ranges (reference dish portion ranges, AI estimate ranges).
  8. **Draft ops per card** (entries + dish group); the confirm use case composes the `ChangeSet` with that card’s `Origin.proposal(id)`.
- **Recompute API:** pick a chip option, answer a question, change an amount/unit, swap the food (alternatives or a search result), remove/add an item, change slot/time. Each returns a new draft + a **diff** (what changed, for UX-024 highlighting).
- **Persistence re-slice approved 2026-10-24 (PA1):** A21 returns draft ops and a versioned session codec; **A23 owns the `proposals` table, migration, resolve-proposal op and outcomes**. A22 creates/owns `chat_messages` and saves the message before sending. B18 supplies the server sync entities contract first; A23 consumes it. No proposal persistence in A21.
- **For the eval:** a small, documented `fb_domain` entry point (interpretation in → draft + metrics-relevant fields out) that B09 wires into `buddy_eval` for the full AQ metrics.

### 1. Summary

Build an immutable, pure-Dart food proposal engine, shared by the phone and the B09 eval. One **message-level** evaluation resolves all food cards together, computes numbers with the existing nutrition primitives, allocates at most two questions across the reply, and returns draft diary ops and typed changes for highlighting. Every tap reduces the saved inputs and recomputes from source facts; nothing accumulates into previous totals. The app adapter loads local food/yield facts before evaluation and snapshots `ClientConfig`; neither build nor recompute performs I/O. A22 owns presentation, `chat_messages` and the confirm use case; A23 adds durable per-card proposals, resolve ops and outcome recording to that use case. A21 supplies the versioned draft codec but adds **no persisted table or migration** (D9).

### 3. Design: files and public API

**Existing boundaries.** `fb_domain` has no runtime dependencies; keep its allowlist unchanged. The app's generated `fb_api_client` remains the API DTO owner, with no hand edits or duplicate wire DTO classes. Domain types below are normalized computation inputs, not replacements for generated transport types. App code uses generated `BuddyInterpretation.toJson()` at the boundary; eval can pass the identical recorded JSON. A single pure decoder converts that JSON directly into normalized domain values and fixed-code failures, without Flutter or the generated client's dependency graph. Schema/real-response fixture tests pin the decoder to B08. The engine does not use the unshipped intents from `06` as if they existed.

One card per meal, coalescing food intents for the same resolved date/slot in stable order; each has its own ID, lifecycle, draft ops and readiness, with group IDs for its distinct dishes. Result also exposes routing outcomes for nonfood intents and one shared bounded message question set. A22’s confirm use case composes `ChangeSet(card.draftOps, origin: Origin.proposal(card.id))`; A23 appends resolve-status/outcome and message-budget ops there in the same ChangeSet. Neither total preview nor ChangeSet construction sums sibling cards. Recompute accepts lifecycle/context updates from the application; it cannot reconfirm confirmed/discarded cards. Actual lifecycle changes come from successful applier transactions, never optimistic engine writes.

**Codec and sync (PA16–PA18/PA25).** The message budget is stored **once** as a bounded versioned JSON field on the **assistant `chat_messages` row** (A22 table / B18 `chatMessage` entity). It holds effective thresholds, issued question IDs (≤2 ever), card ownership, open/answered state and expected card IDs. The codec exposes a separate message-budget projection and compact per-card projection. Proposal rows contain card state/owned question IDs, immutable `originMessageId` and current `budgetMessageId`; no shared-budget copies. Restore takes the assistant message row + its cards selected by `budgetMessageId`, checks cardinality, owned-ID union, ownership/open-state agreement and lifecycle, and recomputes derived numbers. Missing message/card rows → `sessionIncomplete`; present but inconsistent rows or >2 issued IDs → `budgetConflict`. It never allocates IDs or trusts stored ops. B18 validates **no cross-row consistency**; all those checks stay in A21’s pure restore with application recovery in A23.

On rebuild M1→M2, retain `originMessageId=M1`, set `budgetMessageId=M2`, and count still-open carried question IDs in M2’s one budget field before new questions. M1 keeps its issued history; it must not require a moved card as a current member. A23 updates changed card, M2 budget and any changed M1 membership together in one ChangeSet; restoring M2 loads its current cards even when their origin is M1. Stored statuses are `pending / confirmed / discarded / superseded`; engine `active ≡ pending`, and A21 never produces `superseded` (follow-up updates in place). A stored superseded card is historical/nonconfirmable, not silently reactivated.

A21 local input limit is **512 KiB**; B18 bounds each JSON string to **32768 UTF-16 units**, with a `codecVersion` integer and opaque interpretation/draft/message-budget JSON. The per-card projection removes mention/reason/model text, duplicate facts and derived ops/totals/previews; keeps selected/alternative facts, original quantities, choices, IDs, provenance, lifecycle and owned question IDs needed for offline recompute. `interpretation` contains **only this card’s normalized intents**, referring to facts/options held once in compact card JSON; never all sibling intents or a second facts/options copy. Shared budget resides only on its assistant message. Six-item fixtures must fit each bounded field at ≤32768 UTF-16 units; pin supplementary-character boundaries (not byte or Unicode scalar counts). If irreducibly too large, return `syncPayloadTooLarge`, keep full local pending state and expose A23 split/reduce-before-sync recovery; never truncate essential data or acknowledge an oversized row as synced.

`ProposalEvaluation` projects **the same engine and fact precedence**: card IDs/lifecycle, selected FoodRef/source/fact origin, canonical amounts, nutrients/ranges, estimate flags, state/slot/day, assumptions/origins, `questionKind`, question counts and readiness.
