_Old ID: S32 (renumbered by TD-063, 2026-10-16)._

**Goal.** The deterministic heart of Buddy on the phone: turn an interpretation into a proposal draft (numbers, assumption chips, at most two questions, "today after this") and recompute instantly on every tap, with no network and no AI cost.

**Spec:** AI-020, AI-021, AI-022, AI-023, AI-031, AI-032, AI-033, AI-034, AI-040–043 (recompute side), AI-060, AI-061, AI-062, AI-063, AI-064, AI-101 (shares), FD-060, FD-061, FD-062, D-072, AQ-04, AQ-05, AQ-06, AQ-07, AQ-08, AQ-10 · **Decisions:** TD-009

## Scope
- **`ProposalEngine`** in `fb_domain` (`06` §3.3):
  1. Resolve each dimension: stated → saved default (memory, from A26. Empty for now) → question candidate.
  2. Compute kcal per option. **Ask only if** the options differ by > 20% **and** > 50 kcal (thresholds from `/v1/config`). Keep **≤ 2 questions**, ranked by kcal impact. The rest become chips with defaults.
  3. Yields when the stated state ≠ the matched state, with the note.
  4. Cooking fat as its own line, the "all oil eaten" / "most oil left in the pan" chip (FD-061).
  5. Shares ("we were 6", fractions, plates).
  6. Totals (kcal, P, C, F, fiber) + **"today after this"** from local diary + targets.
  7. Estimate ranges (reference dish portion ranges, AI estimate ranges).
  8. **Draft `ChangeSet`** (entries + dish group).
- **Recompute API:** pick a chip option, answer a question, change an amount/unit, swap the food (alternatives or a search result), remove/add an item, change slot/time. Each returns a new draft + a **diff** (what changed, for UX-024 highlighting).
- **Proposal model** persisted in `proposals` (pending), with the interpretation and the draft as JSON.
- **For the eval:** a small, documented `fb_domain` entry point (interpretation in → draft + metrics-relevant fields out) that B09 wires into `buddy_eval` for the full AQ metrics.

## Out of scope

### 1. Summary

Build an immutable, pure-Dart food proposal engine, shared by the phone and the B09 eval. One **message-level** evaluation resolves all food cards together, computes numbers with the existing nutrition primitives, allocates at most two questions across the reply, and returns draft diary ops and typed changes for highlighting. Every tap reduces the saved inputs and recomputes from source facts; nothing accumulates into previous totals. The app adapter loads local food/yield facts before evaluation and snapshots `ClientConfig`; neither build nor recompute performs I/O. A22 owns presentation and confirmation; A23 owns durable pending proposals. A21 supplies the versioned draft codec but adds **no persisted table or migration** (D9).

A successful result includes one food draft per food intent, one bounded message-level question set referenced by cards, routing outcomes for other intents and typed blocking/nonblocking issues. A `ProposalSession` retains original inputs plus absolute adjustments, not mutable running totals. `ProposalEvaluation` is only a projection of `ProposalEngine.build`: stable intent/item IDs, selected FoodRef/source, canonical amount/unit, kcal/P/C/F/fiber, ranges, estimate flags, resolved state/slot/day, active assumption kinds/origins, questions (kind/options/impact) and readiness. B09's `tools/buddy_eval` calls this entry with API-response JSON and synthetic local context/ID allocations; it owns reference answers, AQ denominators, tolerances, per-language scoring and ≥150-case reporting. A21 must not compute its own AQ pass rate from a few unit scenarios or wire B09's new intents now.

**Facts and units at the boundary.** B08's candidate has **no `basis` or catalog pack version field**. Current catalog release admission requires per-100g; personal candidates require caller-supplied local basis/servings/version. The loader supplies those facts from the same local snapshot, preserves server-resolved numeric facts for the response, and never assumes a per-100ml food is per-100g. Explicit gram/ml basis conflicts produce `factsMismatch`; missing personal metadata produces `missingFoodFacts`. Catalog snapshot includes version, density and yields; absent pack must not erase usable embedded per-100g server facts, but unavailable conversion stays a typed issue. Source mapping pins `personal` → yours, `usda`/database → database, reference → reference; unknown codes fail closed. Candidate `BuddyRange` and `BuddyEstimate.range` are per-100 **nutrient** bounds; serving `rangeLo/rangeHi` are amount bounds on that serving's g/ml basis. They are not interchangeable. Use the matched definition even if an estimate object is also present. Only `match=null` + valid estimate fallback may use AI per-100g midpoint nutrients and scaled bounds, with `FoodRef.estimate`, estimate source, range and forced estimate badge. A guessed serving of a matched food uses the food's nutrients and an estimated amount, never substitutes model nutrient numbers. Replacing it with an explicit measured food clears only obsolete estimate assumptions/ranges; reference-recipe uncertainty stays.

**Confirmation compatibility.** Use the existing A06 `CreateDishGroup`/`LogEntries` and A09 `RequirePersonalFood` guard op where required; confirm-time personal food versions must match the shown source. Generated oil lines use stable preallocated IDs as well. The integration test applies the produced draft through the real in-memory app applier only on a simulated confirm and checks the stored snapshots, group membership, source/range/assumptions and origin. No new handler or writer is planned. If that parity test discovers a missing writer operation or a required contract change, report it to Claude before widening the WP; contract changes need their own contract-first commit by Claude and conformance/Docker gates.
