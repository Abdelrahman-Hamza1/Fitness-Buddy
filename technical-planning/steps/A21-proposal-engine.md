**Goal.** The deterministic heart of Buddy on the phone: turn an interpretation into a proposal draft (numbers, assumption chips, at most two questions, "today after this") and recompute instantly on every tap, with no network and no AI cost.

**Spec:** AI-015 (per-meal cards), AI-044 (follow-up seam), AI-020, AI-021, AI-022, AI-023, AI-031, AI-032, AI-033, AI-034, AI-040–043 (recompute side), AI-060, AI-061, AI-062, AI-063, AI-064, AI-101 (shares), FD-060, FD-061, FD-062, D-072, AQ-04, AQ-05, AQ-06, AQ-07, AQ-08, AQ-10 · **Decisions:** TD-009, TD-081–TD-084 (Proposed)

## Scope
- **`ProposalEngine`** in `fb_domain` (`06` §3.3):
  1. Resolve each dimension: stated → saved default (memory, from A26. Empty for now) → question candidate.
  2. Compute kcal per option. **Ask only if** the options differ by > 20% **and** > 50 kcal (thresholds from `/v1/config`). Keep **≤ 2 questions**, ranked by kcal impact. The rest become chips with defaults.
  3. Yields when the stated state ≠ the matched state, with the note.
  4. Cooking fat as its own line, the "all oil eaten" / "most oil left in the pan" chip (FD-061).
  5. Shares ("we were 6", fractions, plates).
  6. Totals (kcal, P, C, F, fiber) + **"today after this"** from local diary + targets.
  7. Estimate ranges (reference dish portion ranges, AI estimate ranges).
  8. **Draft ops per card** (entries + dish group); the confirm use case composes the `ChangeSet` with that card’s `Origin.proposal(id)`.
- **Recompute API:** pick a chip option, answer a question, change an amount/unit, swap the food (alternatives or a search result), remove/add an item, change slot/time. Each returns a new draft + a **diff** (what changed, for UX-024 highlighting).
- **Persistence re-slice approved 2026-10-24 (PA1):** A21 returns draft ops and a versioned session codec; **A23 owns the `proposals` table, migration, resolve-proposal op and outcomes**. A22 creates/owns `chat_messages` and saves the message before sending. B18 supplies the server sync entities contract first; A23 consumes it. No proposal persistence in A21.
- **For the eval:** a small, documented `fb_domain` entry point (interpretation in → draft + metrics-relevant fields out) that B09 wires into `buddy_eval` for the full AQ metrics.

### 1. Summary

Build an immutable, pure-Dart food proposal engine, shared by the phone and the B09 eval. One **message-level** evaluation resolves all food cards together, computes numbers with the existing nutrition primitives, allocates at most two questions across the reply, and returns draft diary ops and typed changes for highlighting. Every tap reduces the saved inputs and recomputes from source facts; nothing accumulates into previous totals. The app adapter loads local food/yield facts before evaluation and snapshots `ClientConfig`; neither build nor recompute performs I/O. A22 owns presentation, `chat_messages` and the confirm use case; A23 adds durable per-card proposals, resolve ops and outcome recording to that use case. A21 supplies the versioned draft codec but adds **no persisted table or migration** (D9).

One card per meal, coalescing food intents for the same resolved date/slot in stable order; each has its own ID, lifecycle, draft ops and readiness, with group IDs for its distinct dishes. Result also exposes routing outcomes for nonfood intents and one shared bounded message question set. A22’s confirm use case composes `ChangeSet(card.draftOps, origin: Origin.proposal(card.id))`; A23 appends resolve-status/outcome ops there. Neither total preview nor ChangeSet construction sums sibling cards. Recompute accepts lifecycle/context updates from the application; it cannot reconfirm confirmed/discarded cards. Actual lifecycle changes come from successful applier transactions, never optimistic engine writes.

**Codec and sync (PA1/PA2).** Local v1 card JSON contains canonical selected and alternative facts, IDs (including removed/reserved lines), adjustments, per-card lifecycle and message ID, and a versioned shared budget envelope (`messageId`, budget revision, issued question IDs/card ownership, open/answered state and effective thresholds). Shared budget is duplicated in per-card rows because there is no message-session table; restore requires a consistent effective policy, unions issued IDs across **all** rows including confirmed/discarded rows, and rejects >2 IDs or conflicting ownership/choices with fixed `budgetConflict`. A23 loads the message’s row set before opening a card; missing siblings referenced by the envelope are `sessionIncomplete`, not a reset budget. Mixed sync revisions may merge monotonic issued-ID history; inconsistent open/answered or lifecycle state must refresh/reconcile through A23’s versioned resolver rather than guessing or writing from the codec. Restore never allocates IDs, trusts serialized ops or accumulates derived totals.

A21 local input limit is **512 KiB**. B18 sync entity JSON **string fields are ≤32 KiB**; these are separate limits. `encodeCard` has an explicit compact sync projection: remove mention/reason/model text, duplicate candidate definitions, raw response envelopes and derived ops/totals/previews; deduplicate remaining facts by stable key and keep all facts/options, original quantities, choices, IDs, lifecycle and budget required to reproduce the card offline. Persist normalized interpretation rather than the raw model envelope; user text lives in A22’s chat message. Measure both UTF-8 bytes and string code units conservatively ≤32768 per JSON string (B18 pins exact wire length semantics). Do not trim active lines, alternatives, provenance or budget history to fit. A six-item card must round-trip within that bound; an irreducibly oversized card returns `syncPayloadTooLarge`, retains the full local pending state and exposes an A23 split/reduce-before-sync recovery. Never widen B18 limits, silently lose data or declare the oversized row synced. A23’s migration/queue tests own that recovery and B18 admission compatibility.

`ProposalEvaluation` projects **the same engine and fact precedence**: card IDs/lifecycle, selected FoodRef/source/fact origin, canonical amounts, nutrients/ranges, estimate flags, state/slot/day, assumptions/origins, `questionKind`, question counts and readiness. B09 supplies response JSON, a recorded local catalog snapshot/yields and deterministic ID source; it owns reviewer references, AQ denominators/tolerances/per-language scoring and ≥150-case reporting. No duplicate engine policy or AQ population claim from A21 unit scenarios.

**One fact precedence rule (PA6), shared by loader, rebuild and eval.** Personal candidates always use the local personal-food row’s nutrients, basis, servings, names and version (`RequirePersonalFood`), never a stale embedded copy. Catalog/reference candidates use the matching **local pack row when present**; otherwise embedded server facts are eligible only when a whole pack is unavailable and the current B08 per-100g facts can be used without guessing missing metadata. If an attached pack lacks the candidate key, return blocking `missingFoodFacts` until A24 can hydrate/update it; do not silently substitute a similarly named row. Each line records `factOrigin = localPersonal / localCatalog / embeddedServer` and its available version; freeze facts for recompute, refresh only through explicit context/rebuild. Embedded B08 candidates have **no `basis` or `catalogVersion` field**: current catalog admission is per-100g; never guess per-100ml basis or invent a pack version. Recommendation: **A24 hydrates missing keys first**, retain typed failure in A21; additive `BuddyCandidate.catalogVersion/basis` is a future B09/server option, not an A21 contract task. Eval replays the same recorded pack-present/missing-key/pack-absent cases and yields, not preferential server numbers.

Source mapping: personal→yours, usda/database→database, reference→reference; unknown codes fail closed. `BuddyRange`/`BuddyEstimate.range` are per-100 nutrient bounds; serving ranges are amount bounds on their g/ml basis. Matched facts always beat model nutrient estimates. Only `match=null` + valid fallback range may use AI per-100g midpoint nutrients with forced estimate badge/source/range. **No match, no amount and no servings → blocking `needsAmount`** (PA9), never default 100 g; `other` opens amount/search controls (AI-063). Guessed servings on matched food use that food’s nutrients with an estimated amount; measured replacement clears obsolete quantity uncertainty, not reference-recipe uncertainty.
