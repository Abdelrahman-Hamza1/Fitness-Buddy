# A66 — Buddy agent client (app): turn runner, phone tools, conversation, streaming chat

| Track | Depends on | Size | Owner | Status |
|---|---|---|---|---|
| App | A23a, **B25** (contract) | L | Claude (Opus build), Codex review (Risky) | ✅ |

**Goal.** The app talks to the agent (D-100, AI-160–AI-177): turns stream into the chat with live steps, phone tools answer from local data, the conversation and summary go up with each message, several cards per reply with Apply all, offline and failure handling (A23b's scope), and the dev trace view. The app switches from `/interpret` to `/turns`.

**Read first:** `spec/10` §4, §15, `06` §3, §6, §11, TD-125–TD-128, A22/A23 cards (A23b's written plan for the queue, failures and pending strip).

## Scope (work packages, one commit each)
- **WP1 Protocol:** turn runner over the generated types and a small SSE framing reader (event ids, heartbeats, ordered `text` chunks); start/continue; `ackTurn`; `error` handling; idempotent `turnId` = message ID; stop = close the stream (and never post a pending `continue`); late events ignored.
- **WP2 Persistence and recovery:** the durable **turn checkpoint** (request or continuation + results last sent, last event id, received proposals) and the retry rule (same round once with `priorAttempt`, never after a user stop, then failed with "Try again"); `ProposalSessionWriter` create/update by `proposalId` + `revision` (stale revisions dropped); on a retry keep the earlier attempt's confirmed cards and drop its still-pending ones when the retry's first proposal or `done` arrives; the **"possible duplicate"** hint when a card's food, meal and amount match one confirmed earlier in the same turn; the **`buddySummary`** entity (local table + sync codec, server admission from B25 WP1) and compaction (evicted entries past the watermark → `compact`, store the returned summary only if the revision still matches); message queue offline/unavailable and failures (A23b scope, AI-045, AI-047, AI-153).
- **WP3 Request builder and phone tools:** history (≤ 12 with outcomes by `proposalId`), personal slice (≤ 20 local matches against the message tokens, with facts), profile (memory slice when `memoryItem` exists, confirmed defaults, halal, units, Ramadan), snapshot (open cards with revisions); phone tools `find_my_foods`, `read_diary`, `read_body`, `read_workouts`, `read_memory` with the `06` §4.2 scopes enforced on the phone and the per-turn disclosure budget (≤ 120 rows, 48 KiB); unknown tools → `ok:false unsupported`.
- **WP4 Chat UI:** live step line (ARB per step code), reply text, question chips (AI-166), several cards per reply with **Apply all** (still-pending current revisions only, one ChangeSet, one Undo; AI-162), cards updating in place, stop button, pending strip and "{n} waiting", a minimal summary row in Buddy remembers (full screen in A67); existing food and weigh-in cards from `proposal` events, other kinds "Buddy can't do that in this version yet" until A67–A69.
- **WP5 Trace and switch:** trace view (AI-172) in dev and owner builds only (`trace: true`), local only, never synced; remove the interpret request path (B26 removes the server side).
- **Tests (TD-128):** only the confirmation guard (a `proposal` event never reaches `ChangeSetApplier` without a user action; Apply all applies only still-pending current revisions of that reply). Tests covering removed interpret code go with it; `make check-*` gates pass.

## Exit criteria
1. On the A55 against the laptop server: "2 eggs" → card in ≤ 5 s; "same as yesterday's lunch" → a `read_diary` round trip → card; a question → chips → answer continues; Apply all on a 3-card reply; stop mid-turn; kill the app mid-turn → resumes without duplicate cards; airplane mode → pending, then processed.
2. Trace view shows each step in the owner's build only.
3. CI green; Codex code + security review passed.

| # | Decision | Why |

| D1 | **Transport:** `BuddyTurnApi` (data) posts the generated `BuddyTurnStart`/`BuddyTurnContinue` JSON with dio (`ResponseType.stream`, `Accept: text/event-stream`, `Idempotency-Key` = `turnId`) on a clone of the app dio (auth/client interceptors kept, like `BuddyApi`). The generated retrofit methods can't stream, so only the request/response *types* are generated; the path strings come from the contract. A hand-written `SseFrameReader` (UTF-8, `\n`/`\r\n`, `id:`, multi-line `data:`, `:` heartbeat comments ignored, blank-line dispatch) yields frames; `data` is decoded with the generated `BuddyTurnEvent.fromJson`, and the raw `intent` map is kept for proposals (the loader reads raw JSON, as for interpret). 30 s idle receive timeout (heartbeat every 10 s). | TD-125; contract-first |
| D2 | **Runner:** `BuddyTurnRunner` (application) runs one turn round by round over ports (api, tools, sink). Per round it drops events whose SSE id isn't `{turnId}:{round}:{seq}` with a growing `seq` (duplicates/late), stops on the first terminal event (`phoneTools`, `done`, `error`), and ignores everything after a user stop (the stream subscription is cancelled; a pending `continue` is never posted). Unknown event types are ignored. | §3.3, §2 cancellation |
| D3 | **Failure classes:** before the stream: connection error / connect timeout / 5xx / 503 → **pending** (same body, same attempt, AI-047/153; never counted as the retry); 429 → failed (limit copy); 400/401/409/422/426 → failed. A stream that breaks before a terminal event, an `error unavailable\|timeout` event, or a checkpoint found after a restart → **the one retry** (same body + `priorAttempt`, attempt 2); a second ambiguous end, `error invalid\|roundAlreadyRan\|expired` → failed with Try again (= the text as a **new** message, new `turnId`). A user stop never retries. | §3.4, A23b D18 kept where compatible |
| D4 | **Checkpoint** (local only): JSON in the user row's existing local `request_json` column (TD-102), written by a new op `SaveTurnCheckpoint(id, json?)` (chat family, user rows only, ≤ 512 KiB): `{round, attempt, kind start\|continue, body, lastEventId, stopped, disclosure {rows, bytes}, cards [{p proposalId, c cardId, r revision, a attempt}]}`. Written with `processing` before the first post, before each `continue`, and **in the same change set** as each card it records; nulled at `done`/`failed`. After a restart (after `ensureRestored`) own `processing` rows with a checkpoint resume by the retry rule; without one they're marked failed once. | §3.4 phone checkpoint, A23b D17 |
| D5 | **Cards from `proposal` events:** each new `proposalId` gets a **holder assistant row** (`replyTo` = user row, text = the card's compact label ≤ 120, local `answer_json` = `{intents:[raw intent], agent:{proposalId, revision}}`), and a one-card session built by the existing loader + `ProposalEngine.build` (card IDs stay UUIDv7; the server's UUIDv5 `proposalId` maps to the card ID in the checkpoint). Written by `ProposalSessionWriter.reply` in one change set with the checkpoint (`Origin.system`, no diary op). Kinds other than `foodLog` (and an unbuildable foodLog) → no card; the reply adds "Buddy can't do that in this version yet." `weighIn` cards stay as today (not built by the engine; A67). | One session per budget message keeps the A23 writer, restore and undo intact; several cards per reply = several holders |
| D6 | **Updates (`replaces`):** resolve `replaces.proposalId` (checkpoint map, else a local card ID the phone sent in `openCards`/history); accept only when the card is open, not mid-confirm, and `expectedRevision` = the card's current revision (in memory; restored cards start at 1; a local adjustment bumps it so a model update can't overwrite it, "changed meanwhile" note); then the existing follow-up path (`ProposalEngine.rebuild` + `ProposalSessionWriter.move`) into a new holder row. Revision ≤ current for a known `proposalId` → duplicate, dropped. Outbound IDs (openCards, history outcomes) are local card IDs; `priorAttempt` uses the server's IDs. | §3.4 identity; one write path |
| D7 | **Retry reconcile:** on the retry's first `proposal` or its `done`, the earlier attempt's still-pending cards that the retry didn't update are resolved `superseded` (system change set, no undo, removed from the thread); confirmed ones stay. A new card whose food keys, slot and amounts equal a card confirmed earlier in the same turn shows "possible duplicate". | §3.4 reconcile |
| D8 | **Reply row:** at the terminal event, one assistant row with the streamed text (or the question text; or a fixed line when nothing came), local `answer_json` `{question:{options}, trace:[…]}` (chips survive a restart; trace local only, never synced: the sync mapper is an allowlist). `summary` events → `buddySummary` only when the stored revision is still `previousRevision`. | AI-165–167, AI-172 |
| D9 | **`buddySummary`:** drift table `buddy_summaries` (SyncColumns + text, revision, watermark), schema **v17** (`from_16_to_17`: create table, indexes, sync triggers), op family `buddySummary` (`SaveBuddySummary(id, text, revision, watermark, expectedRevision)`, `ClearBuddySummary(id)`), sync codec v1 in `buddySyncCodecs`; the live row with the highest revision wins. `pendingAppTables` loses `buddySummary`. | §6.2 |
| D10 | **Request builder** (`BuddyTurnContextReader`, one read snapshot): history = last 12 entries (user rows + each turn's reply text, buddy entries carry their turn's card outcomes: pending/confirmed(unchanged)/edited(adjusted)/discarded, label = holder text); compaction = entries past the window and after the watermark (≤ 24 newest, watermark past the rest); personal slice = personal foods sharing a normalized word (the interpret matcher, moved; saved meals/batches/usual come with A67); profile = memory `[]` until A67's table, defaults `[]` (the engine applies saved defaults itself), halal/units from settings, Ramadan from the active plan when readable else inactive; snapshot = now, tz, active slots, today's confirmed totals + targets, ≤ 5 open cards with revisions. `ackTurn` = the previous done turn. | §3.1, TD-126 |
| D11 | **Phone tools** (`application/tools/`): `findMyFoods` (personal foods ≤ 20), `readDiary` (≤ 31 days, ≤ 40 rows), `readBody` (raw ≤ 31 days/31 rows, trend ≤ 365 days as aggregates), `readWorkouts` (≤ 90 days, ≤ 15 sessions), `readMemory` (≤ 30; empty until A67), `queryData` → `ok:false unsupportedPlan` (A68). **Assumptions B25 must match:**
1. Every event's SSE `id` is `{turnId}:{round}:{seq}` with `seq` strictly increasing within a round (the phone drops mismatched or non-increasing ids; a frame without an id is accepted).
2. Start is round 0; `phoneTools.round` is the round the phone posts next.
3. (Revised with B25, decision b.) Only clear pre-admission refusals keep the attempt: no connection, 503 before any stream (re-posted later as is), 400/401/426 (failed), 409 (failed), 429 (limit). Anything ambiguous (reset/timeout after sending, other 5xx, a stream without a terminal event, `error unavailable|timeout`) is retried once as attempt 2 with `priorAttempt` (an empty card list when nothing arrived); the server runs `attempt = 1` priors when no round started.
4. `openCards[].proposalId` and history `outcomes[].proposalId` are opaque to the server (local card IDs) and are echoed back in `replaces.proposalId`; in-turn updates use the server's own UUIDv5.
5. The continue body is exactly `{turnId, round, continuation, results, priorAttempt}`; an unknown tool name gets the `unsupported` result variant `{name:"unsupported", callId, ok:false, error:"unsupported"}` (decision c). `priorAttempt.cards[]` carry `revision` (decision a).
6. `summary.revision` = `compact.previousRevision + 1`.

**Codex should review hardest:** (a) the confirmation guard: no `proposal` path reaches a diary op (`AgentCardWriter`, `_proposal`, `_supersede`); (b) `applyAll` + group Undo (one change set across sessions, only `confirming`+`canConfirm` cards, reopen of every card of the entry); (c) retry/resume: checkpoint encoding, `_resumeWaiting` (own rows only, stopped turns never resumed), the reconcile on the retry's first proposal/done, duplicate/stale revision drops; (d) phone-tool scopes and the disclosure budget (clamping, row/byte counting, budgetExceeded); (e) generation safety: runners stopped and writes dropped on a profile switch; (f) nothing logged (no `print`/reporting of texts, events or results).
