# A70 — Voice input in Buddy (app)

| Track | Depends on | Size | Owner | Status |
|---|---|---|---|---|
| App | A66 | S–M | Claude (Opus build), Codex review | ✅ |

**Goal.** Speak to Buddy: a mic in the composer, on-device speech recognition with live words, and the transcript in the message box to fix before sending (AI-014, D-101). Design: the owner's canvas (boards "Speak 1–3", "Ask"; https://claude.ai/artifact/J4SeT5YnJzhY8McY4PLx4k).

## Scope
1. Mic button in the Buddy composer (next to the photo button). Tap → a listening panel: English / عربي switch (remembered), live words, level bars, Cancel, tap to stop; stops on its own after a pause.
2. Done → the words go into the message box (appended to anything already typed), focused, a hint "From your voice: fix anything, then send". Never auto-sent.
3. On-device recognition via the platform speech service (a plugin chosen in the plan); `RECORD_AUDIO` asked on first use with a plain explanation; denied / no recognizer / no Arabic pack → a plain message and the keyboard. No audio stored, logged or sent by the app; transcripts are not logged.
4. **Entry point for A71:** `BuddyEntry` — open Buddy in mode `keyboard` (composer focused) or `voice` (listening panel opens at once). One public function/provider the widget step calls; used by the app's own Buddy bar too where it fits.
5. Tests (TD-128, lean): the transcript lands in the box and is never sent by itself; permission denied falls back to the keyboard.

## Exit criteria
1. On the A55: Speak "had a chicken shawarma sandwich and a laban for lunch" → words in the box → send → lunch card. Same in Arabic.
2. CI green; Codex review passed.

## Outcome

_Final (2026-11-07), on `e3b82661`. Not pushed; review and merge are the orchestrator's._

**Built:** WP1–WP3 as planned. Size: S–M.

**`BuddyEntry` (for A71):** `import 'package:fb_mobile/features/buddy/buddy.dart';`
- `enum BuddyEntryMode { keyboard, voice }`
- `BuddyEntry.open(BuildContext context, {required LocalDate date, BuddyEntryMode mode = BuddyEntryMode.keyboard, bool revealPending = false}) → Future<void>`; shorthands `BuddyEntry.keyboard(context, date: …, revealPending: …)` and `BuddyEntry.voice(context, date: …)`.
- Route form (no context needed): `TodayRoute(open: TodayOpen.buddyVoice)` (`/today?open=buddy-voice`), next to the existing `TodayOpen.buddy` (keyboard); Today opens it once through `BuddyEntry`.

**Deviations / notes:**
- **On-device only, no off-device retry (Codex review 1):** every session asks for `onDevice: true`; a language the recogniser doesn't list (on Android 13+ with an on-device service that list is the on-device languages) or a `language_unavailable/not_supported` error ends in "Your phone can't recognise this language yet…" and the keyboard. **Residual:** on a phone without an on-device service the plugin silently uses the phone's standard recogniser, and `EXTRA_PREFER_OFFLINE` is a preference Android doesn't guarantee, so the phone's own speech service may work online. The app keeps no recording and sends nothing until Send; the first-use explanation says so plainly ("Your phone's speech service turns your voice into words, and may use the internet to do it…"), never "stays on the phone". A strict check (`hasOnDeviceSupport`) exists only in the plugin's 7.6 betas: revisit when it is stable.
- **Denied vs denied for good aren't told apart** (no `permission_handler`): both show "microphone access is off… turn it on in your phone's settings, or type instead". A permission revoked after a first successful start shows the same message on the next try.
- The panel is a modal sheet over the Buddy sheet (so the keyboard goes away while listening); its height changes between the explanation / listening / message states, never while words come in (3-line box at the current text scale).
- No goldens changed (no Buddy sheet golden exists); Patrol: no composer copy changed ("Search foods", "Tell Buddy what you ate" unchanged).
- Android build not run here (no APK): the plugin's manifest is empty (minSdk 21 ≤ app 26); the merge run's `android`/hardening job is the build evidence. `RECORD_AUDIO` isn't on the hardening deny list.

**Codex should review hardest:** (a) never auto-sent: `_speak` only sets the controller's text; `_send` is the only path to `send()`; (b) no transcript in logs: `SpeechWords.toString` hides the words, platform errors are swallowed without text, plugin `debugLogging` off; (c) stale-session handling in `PlatformSpeechRecognizer` (`_retrying`, `_session` identity, Stop grace) and `VoiceInputController` (session counter, dispose cancels).

**Owner device checks (exit 1, A55):** Buddy bar → mic → first time the explanation → Allow → speak "had a chicken shawarma sandwich and a laban for lunch" → words live → pause (auto-stop) or Done → words in the box with the hint → Send → lunch card. Switch to عربي → speak Arabic → same. Deny the permission once → the plain message → Type instead → keyboard. If Arabic says "can't recognise this language yet", add Arabic in the phone's speech/offline-recognition settings (or report: it means the standard recogniser lacks it too).
