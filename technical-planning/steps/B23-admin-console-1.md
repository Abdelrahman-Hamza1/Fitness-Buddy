### P1. Design

**Process and network.**
- `FitnessBuddy.Host admin` builds a separate `WebApplication`: `AddFbPlatform` (options, clock, ids, module services), `AddFbObservability("admin")`, the admin pipeline, and **only** the admin endpoints under `/admin`. The `api` role never references the admin endpoint mapping, so the public listener can't serve `/admin` by construction. T2 also checks it.
- Kestrel listens on `Admin:Url` (container `http://0.0.0.0:8081`). Compose publishes it **only** to `127.0.0.1:5197` (laptop stack) or `127.0.0.1:5196` (dev, opt-in profile). **[B23a review]** The console gets **its own tailnet node** `fb-admin` (a pinned `tailscale/tailscale` sidecar in the console's network namespace, `TS_SERVE_CONFIG` HTTPS 443 → `127.0.0.1:8081`, tagged `tag:fb-admin`, never Funnel), so it is `https://fb-admin.<tailnet>.ts.net`: cookies aren't port-isolated, and a shared hostname with the API (the earlier `:8443` plan) would send the console session to the API. No `localhost` console URL on the laptop stack; the loopback port is for readiness only, and only loopback (the sidecar) is a trusted proxy. Chosen over Tailscale Services (`serve --service`) because Services needs a tagged *host*, and tagging the laptop would change its identity and its existing A55 → API policy.
- Why a separate role: the public process holds neither admin routes nor admin DB credentials. One more small container (~120 MB) fits the laptop. Config changes reach `api`/`worker` through the DB.
- The build-time OpenAPI document runs only `api`, so the admin role adds nothing to it. Admin startup validates its options on start (allow-list, client ID, connection).

**Module.** A new `FitnessBuddy.Modules.Admin` project (`Microsoft.NET.Sdk.Razor`, FrameworkReference ASP.NET Core). It is **not** an `IModule` in `ModuleCatalog.All` (no `/v1` group, no OpenAPI tag). `AdminModule.AddAdmin(builder)` / `MapAdmin(app)` are called only by `AdminRole`. Layers:
- `Domain`: pure `ConfigDocument` validation, `ConfigDiff`, the minimum-version ceiling and reach, alert rules (`OverviewAlerts`), CSV escaping, the endpoint capability enum.
- `Application`: one handler per use case (`StartSignIn`, `SignIn`, `StartReAuth`, `ReAuthenticate`, `SignOut`, `SaveConfigDraft`, `PublishConfig`, `RollbackConfig`, `ReadOverview`, `ListAccounts`, `FindAccountByEmail`, `ReadAccount`, `ReadJobsAndSync`, `RetryJob`, `CancelJob`, `SetQueuePaused`, `ReadCatalog`, `ListAudit`, `ExportAudit`); ports `IAdminSessionStore`, `IChallengeStore`, `IAuditLog`, `IConfigDraftStore`, `IAllowList`.
- `Infrastructure`: Npgsql/EF adapters over `admin`, the allow-list file reader.
- `Api`: endpoints + Razor components (`.razor`), static assets (CSS, vendored htmx).
- It reads other modules **only** through their `*.Contracts` interfaces (P4) and BuildingBlocks' `IOpsAdministration` (ops is BuildingBlocks-owned). Every **mutating** contract method takes the caller's `DatabaseSession`, so Admin can put the change and its audit row in one transaction **[R#7]**.

**UI.** Static SSR Razor components (no Blazor circuit, no interactivity, no WebSockets), HTML-encoded by default. htmx (vendored, pinned, P8) enhances filters, the diff preview, the Overview refresh and confirm dialogs. Every page also works as plain forms without JS. Ink & Sky tokens in one `admin.css` as CSS custom properties (light first, from `fb_design_system`'s palette). Status = icon + word (AD-008). At phone width the menu stacks and tables scroll horizontally.

**Errors.** Admin responses are HTML, not the API's RFC 9457 problems (the console isn't part of the contract). A `Result` error becomes a page/partial with plain English and no internals. A 500 shows a generic page with the trace id. An htmx request without a session gets `HX-Redirect: /admin/signin`.

**Remote config moves to the DB (Account module).**
- **One canonical effective config [R#2].** Today the remote-config values come from three places: `Clients:MinimumAppVersion`, `Account:ClientConfig:{FeatureFlags,Thresholds}` and `FeatureFlags:Flags` (server flags). B23a puts them in **one** bound object, `RemoteConfigDefaults` (BuildingBlocks), read from those same keys. The compose files give every role (`migrate`, `api`, `worker`, `admin`) the same values through one shared `x-remote-config` environment anchor, so the migrate role sees exactly what the API sees. The laptop stack today sets none of these keys (image defaults); the anchor makes any future override reach all four roles.
- **Two flag namespaces, kept apart [R#2].** The document holds `featureFlags` = **client** flags (what `/v1/config` returns, from `Account:ClientConfig:FeatureFlags`) and `serverFlags` = **server** flags (what `IFeatureFlags` answers, from `FeatureFlags:Flags`, case-insensitive as today). The server switch `buddy.ai` is a server flag, seeded `true`. Document (internal, `"v": 1`): `{ "v":1, "minimumAppVersion":"0.1.0", "featureFlags":{…}, "thresholds":{…}, "serverFlags":{"buddy.ai":true, …} }`.
- **Seed.** The migrate role, after migrations, inserts version 1 from `RemoteConfigDefaults` when `account.config_versions` is empty (idempotent, under the migration lock). T7a checks seed = defaults for non-default values; T17 checks it on a real upgraded volume with the compose wiring.
- **Cache.** `RuntimeConfigCache` (Account Infrastructure, singleton + hosted poller in `api`, `worker`, `admin`) polls the newest row every 5 s (configurable). Before its first successful read, and when the DB is unreachable at startup, it serves `RemoteConfigDefaults`; after a successful read it keeps the last good value while the DB is unreachable. No poller in `Testing` unless a test turns it on.
- **Ports.** A new BuildingBlocks port `IClientCompatibility { AppVersion MinimumAppVersion }` (default implementation: the options, so Host tests without a DB still work; Account replaces it with the cache). `ClientHeadersMiddleware` (the 426 gate) and `GetClientConfig` both read it, so they can't disagree. `IFeatureFlags` is implemented from `serverFlags`. Buddy: `InterpretMessage` treats `Buddy:Enabled && flags.IsEnabled("buddy.ai")` as enabled, so it returns the existing `Unavailable` result. The console can turn AI off, never on for a server without Buddy configured.
- **Recovery override [R#1].** `Clients:MinimumAppVersionOverride` (environment `Clients__MinimumAppVersionOverride`), when set, **wins over the cache, the DB and the defaults** in both the 426 gate and `/v1/config`. It's read from configuration only, so it works with the DB down or a bad version published. Recovery = set it on `api`, restart `api`, then publish a correct version and remove it. In the runbook; the console shows a banner when an override is active.
- `GET /v1/config`: **same response, same contract**. Expand only: old instances keep reading appsettings.
- Validation: version pattern; client flag names `^[a-z][a-zA-Z0-9_.]{0,63}$`, ≤ 50 flags; thresholds limited to the known keys with `09` §9's accepted ranges; server flags limited to the names present in v1 plus `buddy.ai`.

**Minimum-version safety [R#1].** The kill switch can lock out every app, so the rule for R1 is simple:
- A new minimum may **never be above the newest app version any active install reported in the last 7 days** (from Identity's device activity, which moves into B23a, P4). Lowering it is always allowed.
- If no install reported a version in 7 days, raising is refused ("no active installs to check against").
- The diff shows the reach: "blocks N of M installs active in the last 7 days (versions …)". Raising also needs the new version typed and a recent sign-in (P2).
- Until reach is available (O1 refused or WP4 not done), the minimum-version field is **read-only** in the console; flags and thresholds still work.
- Rollback goes through the same ceiling check (a rollback to an older document can only lower or keep the minimum, unless the ceiling dropped; then it's refused like a raise and the override is the recovery).

**Draft → diff → publish → history → rollback (AD-006) [R#3].**
- One draft row (`admin.config_draft`): `base_version`, `revision` (+1 on every save) and `document_sha256`. Saving a draft is audited.
- The diff page shows the diff for one exact `(base_version, revision, document_sha256)` and puts those three in the publish form.
- Publish, **one transaction**: lock the draft row (`FOR UPDATE`); refuse unless revision and hash match what was reviewed ("the draft changed, review the new diff"); call Account's `PublishAsync(session, document, expectedVersion = base_version, …)`, which takes a transaction advisory lock on the config, checks the newest version is still `base_version` and inserts `base_version + 1` (the version PK also blocks a duplicate); write the audit row with before/after; delete the draft; commit. Two tabs or two publishers: exactly one succeeds, the other gets a refusal and no audit success row (T7d).
- Rollback to version K: same transaction shape, a new version with K's document and `rolled_back_from = K`, with a reason. Published rows are never updated or deleted.
- The cache picks a new version up within one poll interval.

**Maintenance message (AD-012):** deferred (owner item O2). It needs a contract field or a new problem type so the app can show it.

### P2. Auth

- **Allow-list (AD-003/004) [R#4]:** a JSON file at `Admin:AllowListFile` (a private 0600 mount, not git, not the DB): `[{ "handle": "owner", "googleSubject": "…", "email": "…", "role": "operator" }]`. **`googleSubject` is required**; entries without it are invalid. The identity match is the token's `sub` (Google's stable ID) == `googleSubject`, plus `email_verified` and `email` == the entry's email (case-insensitive). It's re-read when the file changes (mtime, at most every 10 s). A missing or invalid file means nobody can sign in (fail closed; readiness reports it).
- **Enrolment (getting the `sub`):** `make serve-phone-admin-allow` writes the entry with the email and no subject yet as a separate `pending` list. A sign-in whose verified email matches a pending entry creates **no session**. It shows the signer their own `sub` and the exact command that pins it (`… --subject <sub>`), and it's audited as `enrolment-needed`. Only pinned entries can sign in.
- **Google sign-in:** Google Identity Services (GIS) button in popup mode, `auto_select=false`, with `Admin:GoogleClientId` = a new **Web** OAuth client (owner action O3).
- **Single-use challenges [R#5]:** `POST /admin/signin/start` (anonymous) creates a challenge row `admin.challenges(id, purpose 'signin', session_id null, nonce_hash, expires_at = +5 min, used_at null)` and sets the pre-auth cookie `__Host-fb-admin-pre` = the challenge id + a random secret (`SameSite=Strict`, 5 min). GIS gets `nonce` = the secret's hash. `POST /admin/signin` verifies the token, then **consumes** the challenge atomically (`UPDATE … SET used_at = now WHERE id = $1 AND used_at IS NULL AND expires_at > now AND nonce_hash = …`); a second use fails. Re-auth uses purpose `reauth` with `session_id` = the current session, so it can't be used from another session.
- **Verifier reuse (B04):** the JWKS fetch, cache and validation in `GoogleIdentityVerifier` move behind a public Identity contract `IGoogleIdTokenVerifier.VerifyAsync(string idToken, IReadOnlyCollection<string> audiences, CancellationToken)` → `VerifiedGoogleToken(Subject, Email, IssuedAt, AuthTime?, Nonce?)?`. Identity's own sign-in keeps calling it with its app client IDs (behaviour unchanged, `GoogleIdentityTests` stay green). Admin passes the web client ID only and also requires the nonce match and `iat` within 2 min of now.
- **Session [R#4]:** a random 256-bit token in the cookie `__Host-fb-admin` (`Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`), stored only as SHA-256 in `admin.sessions` together with **`handle` and `google_subject`**. **12 h absolute**, no sliding. On every request the authentication handler finds the allow-list entry by handle and requires the **same `google_subject`** (and a valid entry). If the entry is gone, re-keyed to another subject, or the handle is reused by someone else, the session is revoked on the spot. The role is re-read from the entry every request, so a demotion takes effect at once. Sign-out revokes the row. Expired, revoked and used rows (sessions, challenges) are deleted on the next sign-in, bounded.
- **Endpoint capabilities [R#10]:** every admin endpoint carries exactly one capability: `Anonymous` (`GET /admin/signin`, `POST /admin/signin/start`, `POST /admin/signin`, static assets, `/health/*`), `Session` (any allow-listed role: every GET, `POST /admin/signout`, re-auth start/finish, and POST-based reads such as the email lookup, which uses POST so the address never sits in a URL), or `Operate` (operator only: every change). The fallback policy is `Session`. T5 enumerates endpoints: each has exactly one capability, the anonymous list is exactly the one above, and every `Operate` endpoint refuses a viewer.
- **CSRF:** the built-in antiforgery on every POST (token in forms and htmx's `hx-headers`) with an **ephemeral** Data Protection key ring (one admin instance; a restart only means reloading the form). Plus `SameSite=Strict` and a check that rejects POSTs whose `Sec-Fetch-Site` isn't `same-origin` or whose `Origin` isn't the request's own origin (the forwarded host/proto from Serve, trusted with the same one-hop rule as `api`).
- **Recent sign-in (AD-007) [R#5]:** `RequireRecentSignIn(15 min)` endpoint filter. Re-auth = a fresh `reauth` challenge for this session, a new GIS credential for the **same `sub`**, the challenge consumed, then `authenticated_at = now`. **Assurance, stated plainly:** if the token carries `auth_time`, it must be within 15 min. GIS tokens usually don't carry it, and GIS can't request `max_age`. Without it, re-auth proves that **the same Google account, signed in on this browser, completed a fresh, single-use, session-bound Google sign-in step in the last 15 minutes by an explicit click** (`auto_select` off). It doesn't prove the Google password was typed again. That's enough for R1 because the console is only reachable over Tailscale on the owner's devices. Stronger assurance (the OAuth code flow with `max_age` and `auth_time`) is a TD-119 option for B13/production. Used in B23 for raising the minimum version; B24 reuses it. Typed confirmation is a form field compared server-side.
- **Hardening:** per-IP rate limits on sign-in start/finish (5/min) and the email lookup (10/min, B23b). Headers on every response: CSP `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; frame-ancestors 'none'; form-action 'self'; base-uri 'none'` (the sign-in and re-auth pages add only `https://accounts.google.com/gsi/` for script, frame, connect and style), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, HSTS over HTTPS. htmx: `allowEval=false`, `includeIndicatorStyles=false`, `selfRequestsOnly=true`.
- **Audit (AD-005):** sign-in, refused sign-in (reason code: `not-allow-listed`, `enrolment-needed`, `bad-token`, `challenge-invalid`, `stale-token`; masked email only), sign-out, re-auth, session revoked by an allow-list change, and every change.
- **Logs:** IDs and codes only (`[LoggerMessage]`): handle, session id, audit id, config version, job id. Never an email, `sub`, token, nonce, cookie, search term, reason text or config value.

### P4. How each window gets its data

The admin process uses `ConnectionStrings:Admin` (`fb_admin`) for everything, through system sessions (no `app.user_id`). Each module exposes a small public interface in its `*.Contracts`, implemented in its own Infrastructure by calling its own `admin_*` functions, so no module touches another's schema and Admin code can't read content even with a bug.

**Counter semantics.**
- **Telemetry SQL inside a caller's transaction runs under a SAVEPOINT [R2#1].** A caught Postgres statement error leaves the transaction aborted, so every counter statement that shares the caller's transaction (the push counters, `touch_device` on the live-session path) runs as `SAVEPOINT telemetry` → statement → `RELEASE`. On a recoverable statement error (`PostgresException`: constraint, check, permission, lock timeout) it does `ROLLBACK TO SAVEPOINT telemetry`, logs the error type and continues. The caller's work then commits normally. Connection loss, cancellation and any `NpgsqlException` that isn't a `PostgresException` **propagate**, so the request fails as today and never reports success for something that wasn't committed.
- **Sync [R#6]:** push outcomes that commit (accepted, stale, invalid per version) upsert `sync_daily` **inside the push transaction** (under the savepoint above), so they commit with it. Logical rejections that end without a commit (pull `datasetMismatch`/`cursorInvalid`, push `datasetMismatch` and any other whole-request rejection) are counted **after** the main transaction rolls back, in a **separate short transaction** for the same authenticated user (same RLS and user lock helper). A successful pull upserts in its own transaction too. An infrastructure failure (exception, timeout, cancellation) records **nothing**. A counter failure never changes the sync response: it's caught, logged as an error type, and dropped.
- **Global counters [R#9]:** OFF lookup outcomes and 5xx counts go to an in-memory accumulator and are flushed every 60 s in one batched upsert per key (no lock contention on the request path). A failed flush is logged and the batch is dropped. It never turns a successful lookup or response into an error. Counts can be lost on a crash, so they're labelled "approximate" in the console.
- **Device activity:** `touch_device` runs on the existing live-session check path; a failure is caught and ignored (the request continues).
- **Running jobs [R#11]:** the worker holds a pending row's lock while it runs and changes its state only at the end, so the queue tables can't tell "running" apart. The worker keeps `busy_type`/`busy_since` in memory and writes them with its 30-s heartbeat. The console shows "**in progress** (as of the last heartbeat): job type, since" per worker, not a precise running count.
