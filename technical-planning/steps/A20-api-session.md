_Old ID: S25 part (renumbered by TD-063, 2026-10-16). The sign-in screens and guest upgrade stay in A33._

**Goal.** The app holds a server session without the user doing anything: an anonymous identity fetched in the background, tokens kept safely and refreshed transparently. Buddy and online search need it (A22, A24).

**Spec:** AC-002 (guest works fully), AC-001 (token handling part) · **Decisions:** TD-024, TD-053

## Scope
- **Auth state** (Riverpod): none / anonymous / registered (the registered path is completed in A33). Tokens in secure storage, per account.
- **Background anonymous token:** when online, `POST /v1/auth/anonymous` after the first frame, **never on the startup path**; retried on reconnect.
- **dio auth interceptor:** attach the access token to the API origin only (backlog #41); on `401`, refresh once (single-flight). Refresh failure or reuse: an **anonymous** session gets a fresh anonymous token; a **registered** session becomes "session expired, sign in again" (A33's flow), keeping its database and data untouched, never silently replaced by a new anonymous user.

## Out of scope
- Sign-in screens, guest upgrade, sign out, per-account database switching (A33).

## Exit criteria
- [x] Cold start makes no auth call before the first frame (test).
- [x] An expired access token is refreshed transparently; concurrent `401`s cause one refresh (fake API tests).
- [x] Refresh failure: anonymous → a new anonymous session; registered → "sign in again" with the local data intact (fake API tests).
- [ ] Against the laptop server (B03): the A55 gets an anonymous token in the background. _(owner check #95; host-side Identity test against the laptop server passed)_

### 1. Summary
The first frame and offline diary remain independent of authentication. After that frame, a keepAlive Riverpod session service restores securely held credentials or creates an anonymous server identity. API requests use a single origin-bound bearer interceptor and one shared refresh operation. Terminal guest-session failure creates a new server guest without touching local data; terminal registered-session failure exposes `sessionExpired` for A33. No sync, sign-in screen, database migration or user-data write is added.

### 7. Risks & unknowns

- **Refresh uncertainty is unavoidable without server replay.** PA2 durably committed before-send pending marker is deliberately conservative: registered users may need to sign in again after a lost response. Never retry a possibly consumed credential. Tests distinguish definite offline/no-send from indeterminate outcome; document this for A33.
- **A33 account ownership is not A20 DB switching.** A20 keeps account kind/id and exposes expiry; no code re-owns rows, wipes data or enables guest sync. A33 must coordinate `acceptAuthenticatedSession` with its own account/database selection and guest merge flow (`05` §6).
- **Secure-storage plugin/build compatibility.** WP1 checks exact selected version, minSdk and native build; existing shared-prefs backup exclusions must cover actual plugin files. Failure blocks WP1; do not substitute preferences. No R2 platform setup in A20.
- **No current configured CI Identity service.** Local enabled-Identity receipt is required; missing Docker access here is Claude's execution responsibility under TD-079. Default tests remain offline/deterministic; no fake pass or opportunistic calls to paid Buddy/provider endpoints.
- **Replay safety.** A20 only transparently retries reproducible, same-account requests after a rejected bearer; no general network retry mechanism. A24/A34 may add explicit upload replay policies later. Auth POSTs remain exempt from response replay caching.
- **Open questions:** none blocking. Recommendation: use the existing local Identity runbook and explicit non-destructive secure-storage options and PA2 native durability barrier; keep CI auth provisioning as a later integration task unless Claude can reuse an isolated fixture without adding secrets to CI.

- **PA1 (non-destructive storage recovery; D3/D4, WP1/WP5).** Explicitly pass `AndroidOptions(resetOnError: false)` through the adapter for reads, writes, pointer operations and deletes; no default-options instance or automatic reset/delete/recreate path. Keep the non-biometric cipher choice. Inspect the **exact pinned release archive/source**, including initialization, migration and decryption recovery, to verify that this configuration cannot erase envelopes, account-kind markers or pointers on Keystore/decryption failure; if another recovery option is required, pin it explicitly too. The reviewed [upstream options](https://github.com/juliansteenbakker/flutter_secure_storage/blob/develop/flutter_secure_storage/lib/options/android_options.dart) and [native recovery code](https://github.com/juliansteenbakker/flutter_secure_storage/blob/develop/flutter_secure_storage/android/src/main/java/com/it_nomads/fluttersecurestorage/FlutterSecureStorage.java) show why defaults are unsafe, but `develop` is not evidence for the release selection. **Tests:** adapter/platform-boundary spies assert option forwarding on every operation; seeded registered envelope, pointer and any present account-kind/recovery-intent marker retain stored Base64 content identity, line breaks ignored, after injected key-unwrapping, initialization and decryption errors. Pointer plaintext is an extra assertion for the ciphertext fault. Native fixtures prove kind through pointer + envelope; intent-marker retention is host-proven only. No deletion/reset calls, `none` transition, anonymous acquisition or credential-bearing diagnostics; expose typed storage-unavailable and preserve any known registered state. Restart/retry remains unavailable until a successful read, never infers an empty store from an exception. Native instrumentation against the pinned plugin corrupts ciphertext and invalidates a test key, checks stored envelope/pointer retention and zero anonymous calls across restart; host mocks alone do not establish plugin recovery behavior.

- **PA2 (concrete crash durability; D4/D8, WP1/WP2/WP5).** Keep credentials exclusively in the secure-storage plugin, and add a **small app-owned Android platform-channel commit barrier on the plugin's actual SharedPreferences backing store**; no plugin fork, plaintext credential file or server change. Android documents that [`commit()` waits for outstanding `apply()` writes on the same preferences and reports persistent-storage success](https://developer.android.com/reference/android/content/SharedPreferences.Editor#apply()). On a serialized background executor, the bridge obtains the same application-context preference name/mode as the pinned plugin and commits a reserved, nonsecret barrier counter with `commit()`. It acknowledges only `true`; timeout, false, exception or lost acknowledgement means unavailable, with no auth send/publish. The barrier key must be outside the plugin's encrypted-key prefix and must not be interpreted as an envelope. - **PA3 (one retry deadline; D7/D9, WP2/WP4).** The coordinator owns one monotonic `nextAttemptAt` for automatic acquisition, refresh and recovery, plus failure count and a throttling floor. **Every** automatic entry point checks it before starting a flight: timer, startup/restore, resume, successful same-origin public transport notification, interceptor `401`, `ensureAvailable` and sequential callers. During cooldown, callers get typed retryable-unavailable with remaining delay (or join an existing flight); none starts a new auth call or adds a timer. After each retryable failure set `nextAttemptAt = max(existing deadline, attempt-completion monotonic time + exponential delay, Retry-After floor)`; exponential delays are 1, 2, 4…60 s, but **Retry-After is never capped at 60 s**.
