**Goal.** Our own, secure Identity module: sign-in with Google and email one-time codes, anonymous guests, identity linking that keeps the user ID, and our own tokens, used by every other module.

**Spec:** AC-001, AC-002, AC-003 (server side), AC-041 (no identity leaks) · **Decisions:** TD-024, TD-034

## Scope
- **Schema `identity`:** users (id, created, anonymous flag, status), identities (provider, subject, email, verified), devices, refresh-token families + tokens (hashed), signing keys (`kid`, ES256 private key encrypted at rest, status), email codes (hashed, expiry, attempts), and an audit log (events only, no content).
- **Endpoints** (contract first, `04` §4.3): `auth/anonymous`, `auth/google`, `auth/email/start`, `auth/email/verify`, `auth/refresh`, `auth/logout`, `auth/link/{provider}`, `/.well-known/jwks.json`, `GET /v1/me`.
- **Google:** verify the ID token signature against Google's JWKS (cached), `aud` = our client IDs, `iss`, `exp`, `email_verified`.
- **Email codes:** 6 digits, 10 min, ≤ 5 attempts, throttled per address + IP, constant-time compare. `IEmailSender` port + a dev adapter (codes visible only on the laptop) now. The real vendor adapter, its contract tests and the DNS records (SPF/DKIM) come with production in B14 (TD-064). Plain, bilingual-ready template.
- **Tokens:** access JWT ≈ 15 min (ES256, `sub`, `anon`, `sid`, `kid`). Refresh tokens are opaque, rotated on use, with **reuse detection revoking the family**. Logout revokes the family. Key rotation with overlap.
- **Linking** (AC-003): link to the current anonymous user (same ID). If the identity already belongs to another user → `409` with a typed problem, so the app can offer merge/discard (`05` §6).
- **JwtBearer** for all modules. An authorization policy "registered user" (sync and other account features) vs "any user incl. anonymous" (Buddy, search).
- **Rate limits** on auth endpoints. Audit events (sign-in, link, refresh reuse, logout).
- Contract-test suite for `IEmailSender` adapters. Integration tests for every flow and its abuse cases.

## Out of scope

### Design decisions
- **D1 — Contract handoff first:** add auth/JWKS/me DTOs, anonymous/registered bearer policies, exact error schemas, endpoint-specific throttles and no-store token responses under `contracts/openapi/`. Regenerate with `make gen`; own contract-only commit and Progress-log handoff before server implementation (A20/A33). Token/code POSTs are explicitly exempt from generic replay caching with reasons. Preserve `/v1/config` and existing clients. JWKS root mapping is a Host integration seam; do not invent an alternate `/v1` URL.
- **D2 — Schema and boundaries:** new Identity module with Domain/Application/Infrastructure/Api; only `Identity.Contracts` exposes principal/session/key lookup ports. Schema `identity` owns users, provider identities (unique provider+subject), devices, sessions/refresh families, hashed refresh tokens, encrypted signing keys, email challenges and content-free audit events. UTC clock/UUIDv7 via existing injected ports. Account's `GET /me` calls Identity.Contracts; modules never query one another's tables. All migrations run only in migrate role and use schema-local history.
- **D3 — Pre-auth storage boundary:** authenticated user-owned identity rows use forced RLS and transaction-local identity. Global credential lookups/guest creation/key access cannot rely on an inbound user ID. Use narrowly scoped parameterized database functions owned by fb_migrator, explicit `SECURITY DEFINER`, schema-qualified objects and fixed `search_path = pg_catalog, identity, pg_temp` (pg_temp last), no dynamic SQL, PUBLIC execute revoked, fb_app execution only; any migrator policy exception is limited to identity tables/functions. App role has no direct cross-user credential-table reads/writes. Enumerate every granted function in migration tests, verify arbitrary-user access fails, and review this seam before implementation. Do not give API a migrator connection or a general RLS bypass. The owner accepted this narrow exception to04§6 in TD-077 on2026-10-18 after its purpose and trade-off were explained. Concrete SQL signatures still require review before schema commit. TD-022/025 remain unchanged.

  **Proposed capability inventory (all outputs exclude hashes, key ciphertext and unrelated profile content unless explicitly named):**
  - `create_guest(new_user_id, device_id, issued_session_material)`: server-generated IDs and random token hash only; transaction creates only that fresh principal/session, cannot update an existing user. Caller-supplied existing IDs must fail uniqueness checks.
  - `sign_in_provider(verified_provider, subject, verified_email, new_session_material)`: invoked only after the adapter validates the complete provider token; creates/finds exactly provider+subject. No arbitrary user ID parameter; returned user ID/status and new session ID only. Application typed proof object must not be constructible by request binding. Because fb_app function execution itself cannot verify a Google signature, this deliberately trusts the narrow application adapter boundary and requires the owner/security decision above.
  - `start_email(challenge_id, lookup_hmac, code_hmac, purpose, link_user_id?)`: persistent throttle/expiry/attempt bookkeeping; link_user_id only from a currently live authenticated principal and purpose. No lookup by email exposed externally; challenge start response generic. File sender gets destination/code only in memory after issuance.
  - `consume_email(challenge_id, submitted_code_hmac, purpose, authenticated_link_user_id?)`: row-lock challenge, require correct binding/expiry/remaining attempts; consume exactly once; return verified identity proof or fixed failure. Must never select a user merely from supplied link ID. Link proofs are single-use and principal-bound.
  - `rotate_refresh(presented_token_hash, new_token_hash)`: no user/session ID input; locate exact unguessable bearer hash, row-lock token/family, validate live user/family/expiry, consume or revoke reused family atomically; return only authorized principal/session/token-signing facts.
  - `read_session(validated_jwt_sub, validated_sid)` / `revoke_session(...)`: caller requires a fully validated JWT before use; both IDs must match the same live principal/family. Logout revokes that family only. Lookup failure rejects auth, not anonymous fallback.
  - `link_verified_identity(authenticated_guest_id, provider_proof, session_id)`: one transaction validates current live guest/session, verifies proof binding and unique provider ownership, upgrades exactly that guest and rotates credentials. Any guessed other user/session, consumed/mismatched proof or conflicting ownership fails without mutation. No generic set-user-status operation.
  - `read_keyring` / explicit migrate-role provisioning/rotation: API can read only encrypted signing material/public metadata through a named key access port; no API key-write grant. Master wrapping key is external. Neither API nor functions expose plaintext private keys over HTTP.

  Every function gets adversarial tests with another principal/session/challenge ID, missing/mismatched proof, wrong purpose and simultaneous consumption. Transactions encompass authorization and mutation; success proof cannot be reused after a separate commit. Final concrete SQL signatures/types must be reviewed before schema commit; draft inventory alone is not approval.
- **D4 — Tokens and revocation:** access15min; refresh30-day absolute family expiry,32 random bytes encoded base64url, only SHA256 hashes persisted. ES256, fixed issuer/audience/algorithm, kid/sub/anon/sid, small bounded clock skew (30s), exp/nbf/signature mandatory. Bind sid to a live session/user on authenticated requests so logout/reuse/deletion reject already-issued access tokens immediately; no stale revocation cache. Row-lock refresh family before one-time rotation; concurrent/reused consumed token revokes the family, without storing token responses for replay. Logout is idempotent and family-scoped. Upgrade preserves user ID but rotates session credentials so registered policy derives from current database status, never a stale anon claim. Session/user lookup failures reject authentication; tests cover link/logout/refresh/revocation races and deletion status changes.
- **D5 — Signing key storage:** encrypted PKCS8 in identity.signing_keys using AES256-GCM and a separate32-byte wrapping key from external0600 secret file/secret mount (never DB, source, image or environment example). Fresh cryptographic96-bit nonce per encryption and full128-bit authentication tag; persist nonce/tag/ciphertext/wrapping-key version, authenticate key ID+algorithm+format version as associated data. Public JWK separate. Wrapping-key rotation requires versioned external old/new keys, transactional rewrap of each signing key with a fresh nonce, verification before switching active version, and retention of old wrapping keys until every dependent key is rewrapped or retired. Interrupted rotation must resume safely; recovery needs the protected wrapping-key backup and DB, never regenerate a replacement master key against old ciphertext. New active signing key and old validation key overlap at least maximum access lifetime+skew; only public keys in JWKS. No network/DB/key loading during build-time OpenAPI generation. Key generation/rotation must be explicit tooling, never a new key on ordinary API startup. This new foundation is a candidate TD after plan review, not a silent change to an Accepted TD.
- **D6 — Google:** provider port, trusted fixed Google OIDC/JWKS endpoints and bounded HTTP timeout/cache refresh; signature/algorithm, allowlisted aud, issuer, exp/iat and email_verified validated. Stable provider subject is the identity key; never auto-link accounts by matching email (Google's verification of third-party email alone is insufficient ownership proof). Unknown kid triggers one bounded refresh; stale/failed retrieval fails closed for an unknown key. Offline signed fixtures prove attacks; one owner-driven real test waits for configured Android+server OAuth IDs and B03 HTTPS.
- **D7 — Email:** normalized address plus keyed HMAC lookup for throttles,6digit cryptographic code,10min expiry, at most5 attempts; code hash binds challenge ID/address/purpose using a secret pepper. Generic start result prevents enumeration. Atomic persistent address+IP throttles; production defaults proposed as one send/minute and5/hour/address, with conservative IP limits captured in options/tests. Only newest eligible challenge, attempt consumption and success single-use in one transaction. Never put address/code/token in logs/audit/idempotency cache. Sending uses IEmailSender; a local-file adapter uses explicit `Identity:Email:LocalFile:Enabled` opt-in independent of environment, defaultfalse. The opt-in requires the B03 private deployment path/gates, writes0600 files under a0700 external mounted directory, prunes expired files on issuance and at most one minute after10min expiry, and caps file count; no stdout or telemetry. Production without a configured sender fails safely. B13/B14 configs must reject the local-file option. The laptop Production environment alone never enables it. B14 adds the actual provider and DNS.
- **D8 — Linking:** authenticated guest only, fresh verified Google token or single-use email challenge bound to link purpose/current principal. Unique identity claim and guest upgrade in one locked transaction. Keep UserId; identity owned by another user gives typed409; never merge, discard, transfer rows or trust body user ID. Refresh/session tests cover simultaneous linking and existing identity races. A33 owns merge/discard UX.
- **D9 — Host integration:** JwtBearer + authorization before opted-in idempotency; principal-backed ICurrentUser, `any-user` and `registered-user` policies, content-free401/403 ProblemDetails, no token challenge details. Audit codes/IDs/time only. Auth rate limiting composes with existing per-IP gate, with persistent identity/code throttles and bounded per-user configuration. Existing anonymous config/health and build-time generation remain side-effect free. Update touched old step IDs to B04/B13 where applicable.
